# 业务逻辑白皮书 · 建立与维护（Init）

围绕项目的**业务逻辑白皮书**（根目录一份总览 + `docs/business-logic/` 每模块详细文档），从零建立或对已有白皮书查漏补缺。白皮书是业务逻辑的**唯一事实来源**。

**文档是纯文字大白话**——用自然语言把业务讲清楚，同时把「涉及哪些接口、要不要登录/权限、参数、关联哪些表」也用文字写进去。

> 本文件是骨架。可执行细节在 `references/` 下，进入对应分支时**先读那一份**：
> - `references/mode1-init.md` —— 扫描范围/顺序、子代理拆分、完整性复核、已存在校验
> - `references/module-doc-spec.md` —— 单模块文档每节写到什么颗粒度
>
> 模板在 `assets/`：`业务逻辑白皮书.template.md`、`模块业务逻辑.template.md`

## 先进路由判断

进来先判断这个任务**是否归我管、走哪个分支**：

| 情况 | 分支 | 能否跳过 |
|------|------|----------|
| 项目**还没有**白皮书 | **建立白皮书**（见下） | — |
| 白皮书存在、但某模块为 `待补全`/`草稿` | **查漏补缺**（见 `references/mode1-init.md` 第五节） | 用户只关心某一模块 → 建议先补该模块，或转 `business-logic:improve` |
| 白皮书存在、目标模块 `已核对`、用户说要"完善/改/优化" | **不是我管** → 提示用户用 `business-logic:improve` | — |
| 用户要"照文档写代码" | **不是我管** → 提示用户用 `business-logic:execute` | — |

判断依据：先看根目录《业务逻辑白皮书》(或 `docs/business-logic/`) 是否存在、目标模块状态到没到 `已核对`，再看用户意图。

**与其他技能的关系**：我是流水线第一环。如果用户已完成建档、要优化某块业务逻辑，引导到 `business-logic:improve`；如果要照计划文档写代码，引导到 `business-logic:execute`。

## 贯穿全程的硬约束

1. **纯文字、够用就好**：用大白话写业务；接口/权限/参数/表用文字如实列出（以真实代码/Swagger/数据库为准，不靠函数名臆测）。
2. **白皮书是索引**：根目录白皮书**只做索引**，模块细节永远在 `docs/business-logic/`。任何模块文档改动，必须回根白皮书更新该模块的状态/最近更新。
3. **状态诚实**：`待补全 → 草稿 → 已核对`。只有「已核对」的模块可直接驱动写代码。

知识库结构：
```
<项目根>/业务逻辑白皮书.md        总览+索引（不写模块细节）
docs/business-logic/
├── <模块>.md                    每个业务模块一份纯文字业务逻辑文档
```

## 分支 A：从零建立白皮书

从零把全项目业务逻辑扫出来、建成白皮书。**核心要求：完整——不能漏任何一块业务逻辑。**

模块划分以**后端业务能力**为主导（Controller/Service/定时任务/回调），前端菜单只做验证补充。纯后端模块（库存、定时任务、回调、对账）同样是独立的一等模块。

### 步骤（细节见 `references/mode1-init.md`）

1. **先问：这个项目有几个操作端？**（必问，开放式）——端数决定每个模块要列几套接口，必须先定。
2. **完整扫描 + 枚举全部业务模块**：按 `references/mode1-init.md` 的后端驱动扫描顺序穷尽扫描（Controller/Service → 定时任务 → 回调 → 枚举 → 数据表 → 前端验证），**以业务能力聚合、不以菜单划分**；纯后端五类逐项核对；每张数据库表必须归入一个模块。候选清单**呈现给用户确认增删合并**。
3. **按模块拆子任务/子代理逐个建档**：模块多时用 `superpowers:dispatching-parallel-agents`，每份 `docs/business-logic/<模块>.md` 严格按 `references/module-doc-spec.md` 填满。
4. **完整性交叉复核 + 生成根白皮书**：按 `references/mode1-init.md` 第四节清单逐项打勾；漏了补建。用 `assets/业务逻辑白皮书.template.md` 生成根白皮书 + 在 `CLAUDE.md` 加指针引用。
5. **交接**：汇报建了多少模块、几端、哪些待补全；**问用户**是否进完善或执行阶段（引导到 `business-logic:improve` 或 `business-logic:execute`）。

## 分支 B：已存在 → 查漏补缺

**幂等保护**：根目录已有《业务逻辑白皮书》且 `docs/business-logic/` 有内容 → 不覆盖，转 `references/mode1-init.md` 第五节「已存在 → 查漏补缺」分支。

核心方法：以代码为事实基准、文档为意图基准，**四维双向校验**（章节完整性 / 接口签名 / 数据表字段 / 状态流转）。代码有、文档没有 → 补建登记；文档有、代码已废弃 → 降级标注；偏差大 → 降回 `草稿`、记未决。

## 编排 / 复用的技能

| 场景 | 技能 |
|------|------|
| 模块多、并行建档 | `superpowers:dispatching-parallel-agents` |
| 抽取纯业务流程做辅助（可选） | `business-logic-extractor` |
| 完整性交叉复核 | 按 `references/mode1-init.md` 第四节清单逐项打勾 |

## 铁律速查

- **先路由**：判断是建立还是查漏补缺；不属于我的任务引导到其他技能。
- **进分支先读 reference**：`references/mode1-init.md` 里才是可执行细节。
- **问端数**：开放式问几个端、分别是什么（单端到 N 端都可能），别套死二/三端。
- **不许漏**：按后端→前端顺序扫、纯后端五类逐项核对、每张表归入模块、按清单交叉复核。
- **幂等**：白皮书已存在不覆盖，转查漏补缺。
- **完整性复核是验收关**：按 `references/mode1-init.md` 第四节清单逐项打勾，不是走过场。
