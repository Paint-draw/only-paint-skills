# 单模块业务逻辑文档 · 写作规范（深版）

> SKILL.md 里只有五要素速记；一份 `docs/business-logic/<模块>.md` 到底每节写到什么颗粒度，看这里。模式①建档、模式②完善都以本规范为准。模板见 `assets/模块业务逻辑.template.md`。

**一条总原则**：文档写「业务上发生了什么」，不是「代码怎么写的」，但凡是**能被验证的事实**（接口路径/方法、是否登录、参数、表名、状态流转）都要如实落地——以真实代码 / Swagger / 数据库为准，绝不靠函数名臆测。臆测出来的接口和参数比不写更坏，因为它会被当成事实去写代码。

> **格式是参考，信息才是刚需**：下面各节给的表格列只是一种建议排版。真正要求的是把该有的**信息**写到——方法、登录、权限、参数、关联关系、级联……**用什么列排、方法是单独一列还是并进路径写**（如 `POST /api/app/order`），随项目已有习惯即可。**若项目里已有一套能用的文档格式，沿用它、只补缺的信息，不要为了套这里的列而重排既有文档**（那是无意义的 churn）。

## 〇、模块概述 —— 一段话说清业务边界

模板第一节（"这个模块负责什么"）**不是标题、不是一句话**，而是一段 3-5 句的概要。必须覆盖三件事：

1. **业务领域**：这个模块在业务上管哪一块（如"订单模块管理从用户下单到确认收货的完整交易生命周期"）
2. **核心业务对象**：涉及哪些核心概念、它们之间什么关系（如"核心对象是订单和订单明细行，一个订单包含多行明细，每行关联一个 SKU"）
3. **主要业务操作/流程**：涵盖哪些关键业务动作或流程（如"包含下单锁库存、支付、发货、收货确认、退款/售后等状态流转"）

写完后自检：一个没看过代码的人，读完这一段能不能大致知道这个模块是干什么的？不能就继续写。

> 这段概述的价值：它和白皮书里「模块简介」形成 **概要 → 详情** 的阅读层级。白皮书简介给方向，模块文档概述给边界。两者都写好了，"不知道模块里有什么"的问题才能根治。

## 一、用户操作与页面响应 —— 正向不是全部

最常见的漏是只写「点了成功会怎样」。一个动作要写全四类结局，否则前端只会实现 happy path：

对每个「用户能做的动作」，逐条写：
- **怎么操作**：点击 / 拖动 / 滑动 / 长按 / 直接展示（无需操作）/ 表单输入后提交。
- **触发效果**：点了之后系统在业务上做什么。
- **成功怎么展示**：提示 / 跳转 / 刷新 / 列表增删。
- **失败怎么展示**：错误文案 / 红框 / 停留原页 / 可否重试。失败要分类型——**校验失败**（参数不合法）、**业务失败**（库存不足、已达上限）、**权限失败**、**系统失败**（500/超时）分别展示什么。
- **边界与异常状态**：这是最容易漏的一栏，必须逐项想过——
  - 空态（列表无数据、首次进入）
  - 加载中 / 骨架屏
  - 无权限 / 未登录被拦
  - 重复提交 / 连点（防抖、幂等提示）
  - 并发（两人同时抢最后一件、同一单并发退款）
  - 网络超时 / 断网 / 请求中断
  - 数据过期（进详情时对象已被改/删）

> 判据：把这个动作交给一个没用过系统的人，他能不能靠这段文字预判"我这么点会发生什么、出错会看到什么"。不能就是没写全。

## 二、后台管理对应操作

- **菜单位置**：在后台哪个一级/二级菜单下。
- **增删改查**：能不能新增 / 编辑 / 删除 / 列表查询筛选，各自的业务约束（如"已发布的不能删只能下架"）。
- **审核 / 流转**：是否需要人工审核、上下架、发布/驳回、退款审批等，谁触发、驳回后回到什么状态。
- **权限管理**：哪些角色能操作、需要什么权限点（权限点名称以真实权限定义为准）。

## 三、后端处理逻辑与业务规则

用纯文字讲清「系统怎么算、怎么判、怎么流转」：
- 规则逐条写（如"同一活动每人限购 N 件，超出下单失败并提示已达上限"）。
- **边界/异常的后端处理**：并发怎么防（乐观锁/唯一约束/分布式锁）、重复请求怎么幂等、超时/回调乱序怎么兜底、权限不足怎么拒。前端展示（第一节）和后端处理（这节）要对得上。

## 四、各端接口清单 —— 接口元信息要写全

按项目实际端数，每端一组。不要只写「路径 + 登录 + 权限」，一个接口的完整元信息是：

| 字段 | 说明 | 为什么要写 |
|------|------|-----------|
| 路径 | 如 `/api/app/order/create` | 前端照着调 |
| **请求方法** | GET / POST / PUT / DELETE | 方法错了直接 405；ABP 这类框架非标准动词一律 POST，必须写清 |
| 是否登录 | 是 / 否 | 缺登录态会 401 |
| 是否权限 | 权限点名称 / 否 | 缺权限会 403，且实现类与接口两处授权要一致 |
| 请求参数 | 参数名 + 位置（path/query/body）+ 必填 | 参数放错位置是最高频 400/404 来源 |
| 返回要点 | 关键返回字段 / 分页结构 | 前端渲染依赖 |
| **限流 / 幂等**（如有） | 如"下单接口带幂等键"、"发码接口 60s 一次" | 影响并发与重复提交行为 |
| **版本**（如有） | 如 `/api/v1` vs `/api/v2` 并存 | 多版本并存时不写会调错版本 |

限流、版本这两项**很多项目没有就写「无」**——写「无」也是信息，避免下一个人再去翻一遍。有就必须写，因为它们和第一节的「重复提交/边界」直接相关。

## 五、关联数据表 —— 只列表名等于没写

表名只是入口，真正影响「改这块会不会连累别处」的是**关系与约束**。逐表写：

| 字段 | 说明 |
|------|------|
| 数据表 | 表名 / 实体名 |
| 存什么 | 这张表在业务上装什么 |
| **关联关系** | 和别的表是 1:1 / 1:N / M:N，谁指向谁（如 `Order 1:N OrderItem`） |
| **外键 / 约束** | 有哪些外键、唯一约束（唯一约束往往就是"防重"业务规则的落点） |
| **级联策略** | 删主记录时子记录级联删 / 置空 / 拒绝删；软删还是硬删 |

> 为什么必须写关系和级联：它决定"删一个订单会不会连带删明细/退款记录"、"能不能物理删"。这类信息一旦漏，第七节「影响到的功能」就会跟着漏，是连锁漏。

## 六、影响到的功能 + 原因

本模块一改会牵动哪些别的功能、**为什么**牵动。用 `[[其它模块id]]` 互链，让影响面可被追踪、可被反查（"谁会影响我")。这一节是模式②影响面分析的底稿——底稿越准，改需求时漏改的风险越低。

## 七、状态流转（如有）

业务对象有状态就画全状态机：**每个状态 × 每个事件 → 目标状态**。重点是别只画主干（待支付→已支付→已发货），要覆盖异常支线（超时关闭、支付失败、退款、售后打回）。状态机缺分支是"改一半"的典型来源。没有状态就明写「无状态流转」。

## 八、未决问题 / 溯源

- **未决问题**：代码里没确认清楚、需要人拍板的点，勾选框列出。
- **溯源**：抽取自哪些源码路径 / 设计稿 / 旧系统；最近核对日期。让下一个人能顺着回到证据。
