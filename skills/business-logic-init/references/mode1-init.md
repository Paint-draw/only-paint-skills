# 模式① 建立白皮书 · 扫描与建档方法（深版）

> SKILL.md 给了模式①的 7 步骨架；「怎么扫才不漏、子代理怎么拆、已存在时以谁为基准校验」的可执行细节在这里。

## 一、扫描范围 —— 先划边界，别把整棵树读一遍

大项目直接"完整扫描"会淹死。先明确**扫什么、不扫什么**，再按顺序扫。

**要扫（业务信号所在）：**
- 后端：AppService / Controller / 领域服务 / 领域枚举 / 实体 / Migration。
- 各端页面与路由：小程序 `pages/`、后台 `views/` `router/` `menus/`。
- 后台菜单项、权限点定义。
- 设计稿目录、旧系统源码（业务逻辑的权威参照，本项目里如 `设计页面/`、`太极拳源代码/`）。
- 根 `CLAUDE.md` / `README` / `docs/`（拿技术栈、分层、各端代码位置）。

**不扫（噪音，明确跳过以省 token）：**
- 依赖与产物：`node_modules/`、`bin/`、`obj/`、`dist/`、`.git/`、`packages/`、锁文件。
- 框架脚手架、自动生成代码（如 EF 自动生成的 Migration Designer 文件——看业务用手写的 Up/Down 即可）。
- **测试代码**：默认不作为建档来源（它验证行为、不定义业务）；但当某业务规则只有测试写清了预期时，可回头引用测试作佐证。

## 二、扫描顺序 —— 后端驱动，前端验证

模块划分的**主导因素是后端业务能力**，不是前端菜单树。前端菜单只是验证和补充——纯后端模块（库存、定时任务、回调、对账）在菜单里根本没有入口，但它们是独立的业务模块，和"订单""用户"同等分量。始终记住：**先问"系统有哪些业务能力"，再问"每个能力在哪些端暴露"。**

1. **端**：先确认几个操作端（见 SKILL.md 模式①步骤1，开放式问，别套死2/3端）。端是白皮书骨架——决定每个模块要列几套接口。
2. **后端 Controller / AppService / MinimalApi**：模块的**一等候选清单**。用 Grep 扫 `Controller`、`AppService`、`IApplicationService`、`MapGet/MapPost` 等关键词。每个 Controller/Service 对应一个业务能力——这一层的列表直接决定模块划分的主体结构。
3. **BackgroundService / HostedService / 定时任务**：扫 `BackgroundService`、`IHostedService`、`Timer`、`Quartz`。**这些是独立的业务能力**（如"超时订单自动取消""佣金结算重试""每日对账"），必须各自判定是否单独成模块，不能因为它们没有前端页面就忽略。
4. **外部回调端点 / Webhook 接收**：扫 `callback`、`notify`、`webhook` 路径。支付回调、物流状态推送、第三方审核结果通知——它们有独立的业务处理逻辑，且往往涉及资金/状态变更，是最容易被"按菜单划分"漏掉的一类。
5. **领域枚举 / 状态机**：扫业务枚举（OrderStatus、RefundStatus、CommissionStatus 等）——揭示状态流转骨架，同时反向验证：每个枚举值归属的业务是否都在候选模块清单里。
6. **数据表 / 实体 / DbSet**：扫 `DbSet<>`、`IEntityTypeConfiguration`、Migration 的 `Up()` 方法——**每张表都必须能说出"我归属哪个模块"**。这一步是完整性兜底：前几步没覆盖到的表 = 漏掉的业务模块。
7. **前端页面/路由/菜单**（最后一步，验证补充）：小程序 `pages/`、后台 `views/` `router/` `menus/`。这一步的用途是**验证**——"每个前端页面涉及的业务，在前面几步是否都有对应模块？"以及补出"后端服务不明显但前端确实是独立页面"的模块。**不要反过来**让前端菜单驱动模块划分。

### 纯后端模块类型清单 —— 逐项核对，防漏

以下五类模块**没有前端页面、没有后台菜单**，却是独立的业务模块。扫描时必须按这份清单逐项核对，每类都要在候选模块列表里有对应（确实没有的明写「无」并说明为什么没有）：

| 类型 | 寻找方式 | 典型例子 |
|------|----------|----------|
| 库存/仓储 | 扫 `Stock`、`Inventory`、`Warehouse`、`Sku`（库存维度）实体/服务 | 库存预占/扣减/回补、库存预警、出入库流水、安全库存 |
| 定时任务/后台服务 | 扫 `BackgroundService`、`IHostedService` 子类 | 超时自动关单、佣金分账重试、微信解冻重试、数据归档清理 |
| 外部回调处理 | 扫 Controller 中含 `callback`/`notify`/`webhook` 的路径 | 支付成功回调、退款回调、物流状态推送、第三方审核结果 |
| 统计/报表 | 扫 `Report`、`Statistics`、`Dashboard`、`Summary` 实体/服务；或独立报表 SQL 视图 | 销售统计、用户增长报表、佣金报表、财务报表 |
| 对账/结算 | 扫 `Reconciliation`、`Settlement`、`ProfitSharing`、`Commission` 实体/服务 | 分账结算、佣金计算与发放、第三方对账 |

### 聚合判据：后端业务能力，不是前端菜单

聚合模块时问自己：**"这个 Controller/Service 在业务上负责什么"**，别问"它在哪个菜单下面"。能一句话说清 → 一个模块；一句话里有"和"、要喘口气 → 可能是两个模块，拆开。

前端菜单是聚合**之后**的验证工具——问"这个模块的业务在菜单里能找到对应入口吗？"能 → 模块边界合理；不能 → 分两种情况：(a) 纯后端模块，正常；(b) 前端漏了页面，记入未决问题。

> 用 Glob/Grep 快扫，不逐字读全文件。目标是**枚举出模块清单**，细节留给建档子代理。

## 三、按业务能力聚合成模块 + 子代理拆分判据

**聚合判据**：能不能用一句话说清"它在业务上负责什么"。能 → 一个模块；一句话里有"和"、要喘口气 → 可能是两个模块，拆开。

**子代理拆分判据**（模块多时用 `superpowers:dispatching-parallel-agents`）：
- **按业务模块拆，不按文件数拆**。一个子代理负责 **1 个模块，或 1 组强耦合的相关模块**（如"优惠券+营销活动"经常一起看）。
- 判断"要不要合给一个子代理"：两个模块是否共享同一批表/接口、改一个几乎必然改另一个——是则合，否则分。
- 每个子代理拿到的任务里必须写明：负责哪个模块、产出 `docs/business-logic/<模块>.md`、**前端+后台+后端三侧都要看**、严格按 `references/module-doc-spec.md` 填满、接口/表以真实代码/Swagger/DB 为准。
- 模块少（≤3~4）时不必派子代理，主代理顺序建档即可——派代理的开销只有在"多到会顾此失彼"时才值。

## 四、完整性交叉复核 —— 把"扣10分"换成可核对的清单

「漏一块扣10分」只是提醒完整性重要，**它不是自动扣分机制**，别把它当真的能程序化打分。真正防漏靠这份**交叉复核清单**（所有模块建档后逐项走）：

- [ ] 第二~六步扫出的**每个候选模块**，都有一份 `docs/business-logic/<模块>.md` 了吗？（拿候选清单逐行打勾）
- [ ] 每份文档的**各节都填了**吗（没内容的节要明写"无"，不能留空——留空分不清是"没有"还是"忘了写"）？
- [ ] 有没有**只在单一端出现**、被漏掉的业务？重点再扫：
  - 纯后台业务：审核流、配置项、数据导出。
  - 无界面业务：定时任务（`BackgroundService`/`HostedService`/cron）、外部回调（支付/物流 webhook）、消息消费。
- [ ] **纯后端模块类型清单五类都核对过了吗？**（库存/定时任务/回调/统计/对账）没对应业务的写「无」？有业务但漏建模块的补上？
- [ ] 后端**每个 DbContext 中的 DbSet<> / 每张数据库表**，都能说出它归属哪个模块吗？（表没有归属 = 有业务没建档。每张表必须归入一个模块，跨模块引用的表归属其「主模块」，其他模块在"关联数据表"节声明引用关系。）
- [ ] 后端**枚举里出现的状态**，是否都在某个模块文档的状态流转里被解释了？（枚举值没人管 = 有业务没建档）
- [ ] 候选清单里被"合并/删除"的模块，有没有记一句为什么合/删？

> 复核发现漏 → 补建档，回到第三步。这一步是模式①的验收关，不是走过场。

## 五、「已存在 → 查漏补缺」分支 —— 先定基准，再谈对错

白皮书已存在时**不重建**，做双向校验。**关键是先说清以谁为基准**，否则同一个差异会得出相反结论：

- **代码是"事实"的基准**：接口路径/方法、参数、表结构、状态枚举、权限点——这些以**代码/Swagger/DB 为准**。文档和代码不一致时，默认代码对、文档错（除非代码本身是 bug，那属于模式②要改的需求，另说）。
- **文档是"意图"的基准**：这块业务本该怎么运转、为什么这么设计——以**文档+和用户确认**为准。代码没实现文档写的意图 = 可能是缺陷或待办，记入未决问题。

**双向对照，四个校验维度**（逐模块过——校验的是**信息是否正确、完整**，不是"列有没有和模板长一样"；既有文档格式能用就沿用，别为套模板重排表格）：
1. **章节完整性**：各节该有的信息有没有缺、有没有留空。
2. **接口签名**：文档里的路径/方法/参数/登录/权限，和真实代码/Swagger 是否一致；有没有代码已加、文档没登记的新接口。（限流/版本这类若项目根本没有，写「无」即可，不是缺陷。）
3. **数据表字段**：关联关系/外键/级联信息，和真实实体/DB 是否一致；缺的信息补进去（放哪一列不重要）。
4. **状态流转**：文档状态机的分支，和枚举 + 实际流转代码是否吻合；有没有代码新增了状态、文档没画。

**处理**：
- 代码有、文档没有的**新业务模块** → 补建并在白皮书登记。
- 文档有、代码已废弃的逻辑 → 标注并降级（见下）。
- 某模块偏差大 → 把白皮书里该模块**状态降回 `草稿`**，在该文档「未决问题」记下差异；需要深改就转模式②。
- 收尾更新白皮书「业务模块索引」与「覆盖总览」。

## 六、路径与 CLAUDE.md 引用 —— 消除歧义

- **总览白皮书**：项目**根目录一份** `业务逻辑白皮书.md`，只做**总览 + 索引**（技术栈、端清单、模块索引表、覆盖总览）。它**不写**各模块的详细业务逻辑。
- **各模块详细文档**：全部在 `docs/business-logic/<模块>.md`。
- 两者关系：根目录白皮书是**目录**，`docs/business-logic/` 是**正文**。别把模块细节塞进根文件，也别把索引散到 docs 里。
- **CLAUDE.md 只放一行稳定指针**（如 `> 业务逻辑总览见 [业务逻辑白皮书](业务逻辑白皮书.md)`）。因为它指向的是**文件位置**、不是内容，所以白皮书内容更新时 **CLAUDE.md 不用动**；只有白皮书**改名/移动**时才回来改这一行。这样就不存在"内容一变就要两处同步"的负担。
- **指针里别嵌会漂移的内容**：这一行不要写模块数量、状态统计、更新日期之类**内容派生信息**（如"全项目 33 个业务模块的…"）——模块一增减这行就过期，"稳定指针、内容更新不用动"就名存实亡。数量与状态只在白皮书「覆盖总览」一处维护。已有项目的指针若嵌了这类数字，顺手把数字去掉（如改成"全项目各业务模块"）。
