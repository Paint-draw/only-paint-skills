# business-logic-extractor（内联版）—— 从源码抽纯业务逻辑

> 本文件是 `business-logic-extractor` 技能的完整 SKILL.md 内容内联。模式② 需要「抽取纯业务流程做辅助」时照此执行，不再依赖外部技能。

## 目的

从现有代码库中抽取**纯粹的业务逻辑**，生成一份结构化的业务逻辑文档。

这份文档描述的是：
- **用户能做什么**——操作入口、操作步骤、可见反馈
- **页面如何响应**——状态切换、加载反馈、错误提示、跳转逻辑
- **系统如何处理**——接收到用户操作后的业务处理步骤、规则校验、状态流转
- **业务如何流转**——业务事件触发、外部协作、通知触达

这份文档**不描述**：
- 数据库表结构、字段定义、索引设计
- API 端点、请求响应格式、错误码
- 技术栈、框架、中间件、依赖库
- 数据结构定义、类设计、函数签名
- 部署架构、性能指标、并发控制技术

输出的不是技术文档，而是一份**业务行为说明书**——让产品经理、业务方、或另一个 AI 仅凭此文档就能完整理解这个功能"业务上是怎么运作的"。

## 核心原则

### 1. 纯粹的业务视角

用业务语言描述，禁用技术语言。

| ✅ 应该这样写 | ❌ 不应该这样写 |
|--------------|----------------|
| 用户点击"立即支付"按钮 | 用户触发 onClick 事件 |
| 页面显示加载中状态 | 页面 setState('loading') |
| 系统校验订单是否已支付 | 系统查询 order 表的 status 字段 |
| 支付成功后通知库存系统 | 支付成功后 publish 消息到 RabbitMQ exchange |
| 金额必须大于 0 | amount 字段必须有 CHECK 约束 > 0 |
| 用户每日最多领取 3 张优惠券 | coupon 表对 user_id+date 加唯一索引限制 |
| 订单状态从"待支付"变为"已支付" | order.status 从 PENDING 更新为 SUCCESS |
| 系统调用微信支付完成扣款 | 系统调用 POST /v3/pay/transactions/jsapi |

### 2. 前端 + 后端，缺一不可

业务路径天然横跨前后端：
- **前端**揭示用户交互流程——操作步骤、页面状态、可见反馈、静默请求
- **后端**揭示业务处理链路——规则校验、状态流转、外部协作、事件触发

只看前端 → 不知道系统如何处理业务、规则如何执行
只看后端 → 不知道用户如何操作、页面如何响应、交互如何设计

即使用户说"逻辑都在后端"，前端依然承载交互流程、页面状态、用户反馈这些业务逻辑的一部分。主动分析另一侧，不要等用户提醒。

### 3. 交互流程为核心

前端部分的重点不是"用了什么组件库"，而是**用户操作的完整旅程**：

- 用户在哪个页面、看到什么
- 用户执行什么操作（点击、输入、滑动、长按）
- 操作后页面立即如何响应（按钮禁用、显示加载、弹出确认）
- 是否触发静默请求（后台预加载、状态同步、数据上报、埋点）
- 请求过程中页面如何表现（loading 动画、骨架屏、禁用交互）
- 请求成功后页面如何变化（状态切换、跳转、toast、数据刷新）
- 请求失败后页面如何表现（错误提示、重试入口、状态回退）
- 页面间的跳转逻辑与参数传递（业务层面）
- 页面离开时的处理（未保存提示、轮询停止、资源释放）

### 4. 处理链路为骨架

后端部分的重点不是"调用了什么框架"，而是**业务处理的步骤序列**：

- 接收到用户操作后，系统按什么顺序处理
- 每一步校验什么业务规则（用业务语言描述校验内容）
- 业务状态如何流转（从什么状态到什么状态、触发条件是什么）
- 需要与哪些外部业务方协作（如"通知支付渠道扣款"、"发送短信通知用户"）
- 处理结果如何反馈给用户（成功/失败的业务含义）
- 异常情况下业务如何恢复（补偿、回滚——用业务语言）

### 5. 完整性优先于简洁性

每一条业务规则、每一个交互分支、每一种异常场景都必须被捕获。遗漏一条规则 = 业务理解出现盲区。宁可文档冗长，不可遗漏。

### 6. 追踪而非假设

读真实代码。不要从函数名或文件名推断行为——打开文件，跟随逻辑走一遍。`processPayment` 函数可能根本不处理支付，真正的支付逻辑可能在 `orderService.completeOrder` 里。

### 7. 隐性业务逻辑同样重要

业务逻辑藏在这些地方，都要扫到：
- 测试用例（揭示边界条件和预期业务行为）
- 错误消息与提示文案（揭示业务场景与异常情况）
- 配置项（业务阈值、开关、限额）
- 注释与 TODO（解释业务规则存在的原因）
- 定时任务与后台任务（异步业务逻辑）
- 埋点与日志（揭示业务关键节点）

## 工作流程

### 第一步：明确范围

读任何代码之前，先和用户确认：
- 要梳理哪个功能/业务模块（如"微信支付"、"优惠券核销"）
- 代码库在哪里（目录路径或仓库地址）
- 是否有特定业务场景需要聚焦（如"只看退款流程"）
- 有哪些已知的相关业务需要纳入或排除

如果用户请求模糊，主动追问。"梳理支付逻辑"——是否包含退款、查询、回调？是否包含优惠券抵扣的联动逻辑？范围不清就开始读代码，容易遗漏或越界。

### 第二步：定位所有相关代码

单个功能的业务逻辑通常散落在：

**前端**：页面、组件、状态管理、表单校验、路由配置、API 调用封装、工具函数

**后端**：业务处理逻辑、规则校验、状态管理、外部协作、定时任务、事件处理

**共享**：错误提示文案、业务枚举定义、配置项

**基础设施**：定时任务、后台任务、回调处理、事件监听

按关键词扫描候选文件，然后逐个人工验证文件是否真的相关。

**关键提醒**：不要只靠文件名匹配。`payment.ts` 可能无关，而真正的支付逻辑可能藏在 `order-service.ts` 里。文件名和内容搜索都要用。

### 第三步：深度分析

逐个阅读定位到的文件。对每个文件提取：
- 它承载了什么业务行为
- 用户在这里能做什么操作
- 页面/系统如何响应
- 业务规则是什么
- 它处理了哪些边界情况
- 它与哪些其他业务环节连接

**追踪完整的业务旅程**：选一个用户动作（如"用户点击支付"），跟随它穿过每一层——前端操作 → 页面响应 → 静默请求 → 后端接收 → 业务校验 → 状态流转 → 外部协作 → 结果反馈 → 页面更新 → 用户可见结果。记录每一步的业务含义。

### 第四步：综合成业务逻辑文档

将所有发现整合成一份结构化文档（顶层章节：功能概述 / 业务术语表 / 用户角色与权限 / 用户交互流程 / 系统处理链路 / 业务规则 / 业务状态流转 / 业务事件与通知 / 边界情况与异常处理 / 业务流程全景图 / 待确认问题）。

文档必须自包含——一个无法访问原始代码库的产品经理或业务方应当能仅凭此文档完整理解这个功能"业务上是怎么运作的"。

### 第五步：完整性检查

定稿前，逐项过一遍业务关键点。常见容易遗漏的点：
- 页面的加载态、错误态、空态、禁用态
- 静默请求（用户无感但系统在后台做的事）
- 防重复操作（按钮禁用、节流）
- 业务规则的触发时机与优先级
- 异常场景下的业务恢复
- 跨页面的状态传递与一致性
- 定时任务触发的业务行为
- 外部回调引发的业务流转
- 并发操作下的业务表现（如两人同时抢同一资源）

### 第六步：技术净化审查

定稿前，通读全文，**逐句检查是否残留技术语言**。任何出现以下词汇的句子都要改写：

- 数据库、表、字段、索引、外键、SQL、ORM
- API、端点、HTTP、请求体、响应体、状态码、REST、GraphQL
- 框架名、库名、中间件名（Spring、React、Redis、RabbitMQ 等）
- 类、对象、方法、函数、变量、接口（技术含义）
- JSON、XML、序列化、反序列化
- 缓存、队列、线程、进程、连接池
- 部署、容器、微服务、网关

**例外**：当且仅当某个技术名词本身就是业务术语时才可保留（如"微信支付"、"支付宝"、"短信网关"等外部业务方名称）。

### 第七步：输出

将最终文档保存为 Markdown 文件到 `/home/z/my-project/download/[功能名]-业务逻辑.md`（项目里有既定习惯就沿用它）。功能较大时拆分为多个文件加一个索引文件。

## 重要提醒

- **永远不要跳过前端**。前端承载用户交互流程、页面状态、用户反馈，是业务逻辑的第一现场。
- **永远不要跳过后端**。后端承载业务处理、规则执行、状态流转，是业务逻辑的核心。
- **永远不要输出技术细节**。数据库、API、技术栈、数据结构都不应出现在最终文档中。如果发现自己在写"系统查询 X 表"或"调用 Y 接口"，立即改写为业务语言。
- **仔细读测试**。测试往往揭示实现代码中不明显的边界条件和预期业务行为。
- **留意注释和 TODO**。它们有时解释业务规则存在的原因，这对理解业务至关重要。
- **捕获"为什么"，不只是"是什么"**。如果某条业务规则因合规或业务原因存在，记录这个原因。
- **区分硬约束与软约束**。"金额必须大于 0"是硬约束；"建议用户名至少 4 位"是软约束。文档中要标明。
- **记录不确定性**。如果某段代码的业务行为无法确定，明确标注"此处业务行为需向用户确认"。
- **静默请求是业务逻辑**。用户无感但系统在后台做的事（预加载、状态同步、埋点上报、轮询刷新）都是业务逻辑的一部分，必须记录。
- **页面状态切换是业务逻辑**。按钮何时禁用、页面何时 loading、何时显示错误——这些都是业务规则的可视化表达。
