# 模式② 完善 / 优化业务逻辑 · 方法（深版）

> SKILL.md 给了"先确认需求 → 出完善文档 → 出计划文档 → 过对抗式审查门"的骨架；每步的判据、话术清单、非功能维度、冲突上报、完成标准在这里。模板见 `assets/完善文档.template.md`、`assets/计划文档.template.md`。

## 核心原则：三顶帽子思考法

模式②不只是一个"把需求写清楚"的过程——你需要同时戴上**三顶帽子**，从三个专业角色出发审视每一个业务改动。这不是三个独立的步骤，而是分析每一个决策点时要同时切换的三种视角：

### 🎩 帽子一：高级产品经理（业务价值 & 逻辑完备性）
戴上这顶帽子时，关注：
- **用户价值**：这个改动解决谁的什么问题？不做会怎样？有没有更简单的方案达到同样目的？
- **业务流程完整性**：正向路径、失败路径、边界条件、异常恢复——每个分支都有人处理了吗？用户在任何一步"卡住"，有没有下一步指引？
- **功能一致性**：新行为和现有功能有没有矛盾？同一个概念在不同页面叫法一样吗？同一个操作在不同入口的行为一致吗？
- **数据兼容**：存量数据在新规则下会变非法吗？新旧数据格式能共存吗？要不要迁移/回填？
- **优先级与分期**：哪些是 MVP 必须上的，哪些可以后续迭代？能拆成多个小需求分批交付吗？

### 🎩 帽子二：高级项目经理（风险 & 交付可控）
戴上这顶帽子时，关注：
- **风险识别**：这个改动最可能在哪里出问题？数据丢失？用户操作中断？旧功能被破坏？
- **发布策略**：能不能灰度/特性开关？要不要停机？出问题怎么快速回滚？
- **依赖与顺序**：先改什么后改什么？哪些步骤有硬依赖不能并行？哪些步骤卡住会堵死整条链？
- **验证闭环**：每步做完怎么验证？谁来验证？什么信号算"过了"？
- **沟通面**：这个改动要通知谁（运营/客服/用户）？要不要写发布公告或操作手册？

### 🎩 帽子三：高级 UI 设计师（用户体验 & 交互品质）
戴上这顶帽子时，关注：
- **交互流程**：用户要几步完成核心操作？能不能更少？每一步的引导是否清晰？操作路径是否可逆（能回退/撤销）？
- **状态覆盖**：每个页面/操作的以下状态都设计了吗——
  - **加载中**（骨架屏/loading/进度条，不是白屏）
  - **空数据**（引导文案+操作入口，不是"暂无数据"四个字）
  - **成功**（反馈明确+下一步引导，不只是 toast 一闪而过）
  - **失败**（错误原因用人话讲+用户能做什么来解决，不是"系统错误"）
  - **权限不足**（明确告诉用户缺什么权限、怎么获得）
  - **网络异常**（离线/超时/接口挂了，分别怎么表现）
- **信息架构**：页面上信息有没有主次？用户最关心的信息是不是最显眼？操作按钮位置是否符合习惯（右下/底部）？
- **一致性**：和现有页面的视觉风格、组件、交互模式一致吗？复用已有的 UI 组件了吗？文案风格统一吗（是全称还是缩写、是"您"还是"你"）？
- **容错与确认**：不可逆操作（删除/支付/提交审核）有二次确认吗？输入有实时校验吗？误操作后能撤销吗？确认弹窗的"取消/确定"文案是否明确表达了后果？
- **无障碍与可用性**：可点击区域够大吗（移动端≥44px）？颜色不是唯一区分信息的方式吗？关键文案是否易懂（不用行话砸用户）？

> **三顶帽子怎么用**：在必问清单的每一项、完善文档的每一节、计划文档的每一步，都同时用这三个视角过一遍。不是"产品先写完→项目经理再审→设计师最后补 UI"，那样会返工。而是**每一项决策都同时问：业务对吗？风险控了吗？用户体验好吗？**

## 零、前置：先读白皮书（模式①的产物是模式②的输入）

动手优化前，**必须先读**该模块的 `docs/business-logic/<模块>.md` + 根目录白皮书里它的「影响到的功能」。理由：不了解现状就提优化，容易重复造轮子、或漏掉被牵连的模块。

- 该模块文档状态是 **`已核对`** → 可信，直接作为"现状"基准。
- 是 **`草稿 / 待补全`** → 现状本身不可信，**先用模式①把现状补到可信，再谈优化**。跳过这步等于在流沙上盖楼。
- 该模块**根本没有文档** → 先走模式①建这一个模块的档，再回来。

## 一、第一步：确认需求（质询法，内联自 grill-with-docs）

确认需求的质询方法完整内容在本技能 `references/grill-with-docs.md`（内联，无外部依赖）。核心是**逐条逼问 + 每个问题给推荐答案 + 一次一个问题**，可查代码的先查代码。

### 质询的输入 / 输出契约

不是甩给用户一句"帮我确认需求"。要明确：

- **喂给用户/带入讨论**：① 现有模块文档路径；② 相关真实代码位置；③ 用户这次想改的一句话诉求；④ 已知的领域术语（CONTEXT.md 如有）。
- **要产出的**：逐条被逼成明确决策的**确认结论**——每条形如「问题 → 用户拍板的答案」。术语对齐结果、边界是否覆盖、受影响功能是否一起改，都要有结论，不能停在"待定"。
- **收回来之后**：把这些结论原样填进完善文档「与用户确认记录」节；带 `[ ]` 的未决项进「未决问题」。

### 必问清单 —— 别只问"改成什么样"

只问"想改成什么样"会漏掉一堆决策点。逐条问过（不适用就明确记"不适用"），每条同时从产品/项目/设计三个角度审视：

- **目标行为**（🎩产品）：改成什么样？正向 + 失败 + 边界分别怎么表现？
- **历史数据**（🎩产品+项目）：已有存量数据怎么办？要不要**数据迁移 / 回填**？旧数据在新逻辑下会不会变非法？
- **兼容与发布**（🎩项目）：要不要停机？能否灰度/开关？旧接口/旧字段要保留还是废弃？出问题怎么回滚？
- **影响面**（🎩产品+项目）：牵动哪些别的功能（照模块文档第六节逐条过），每条**要不要一起改**。
- **非功能维度**（下一节展开）：性能、一致性、幂等、并发。
- **权限与端**（🎩产品+项目）：哪些角色/哪些端受影响，后台要不要加菜单/审核。
- **用户体验**（🎩设计，以下每条都要有答案，不适用写"不适用"）：
  - **交互步骤**：核心操作需要几步？能不能更少？步骤是否可逆/可回退？
  - **加载态**：数据加载时用户看到什么？骨架屏/loading 动画/进度条——不能是白屏或假死。
  - **空数据态**：列表/搜索/筛选结果为空时显示什么？有没有引导用户下一步操作（如"去创建第一个"）？
  - **错误态**：接口报错/请求超时/网络断开时显示什么？错误信息是给人看的话还是技术错误码？有没有告诉用户"你现在能做什么"？
  - **成功反馈**：操作成功怎么告知？toast 一闪而过够不够？需不需要更持续的成功提示（如跳转到结果页、列表刷新并高亮新记录）？
  - **失败反馈**：操作失败怎么告知？表单校验错误是在提交时一次性弹还是实时逐字段标红？错误信息位置在字段旁边还是顶部汇总？
  - **权限不足态**：用户没有权限时看到什么？按钮直接隐藏还是灰掉+提示？点进去才报"无权限"就太晚了。
  - **二次确认**：不可逆操作（删除/支付/提交审核/退款）有确认弹窗吗？弹窗文案是否明确写了操作后果？
  - **信息层次**：页面信息有没有主次？关键操作（主按钮）和次要操作（文字链接/ghost 按钮）视觉上区分开了吗？
  - **文案一致性**：同一个概念在所有页面叫法一致吗？操作按钮的动词统一吗（"保存"/"提交"/"确认"不要混用）？
  - **视觉一致性**：新页面/组件复用了现有设计系统吗？颜色/字号/间距/圆角和已有页面一致吗？还是引入了新样式？
  - **移动端适配**（如涉及小程序/H5）：可点击区域≥44px 了吗？小屏上关键信息会不会被键盘/弹窗挡住？

## 二、需求与现有架构冲突 → 识别并上报，不硬来

用户想要的方向可能和现有技术栈/数据模型打架（如"订单要支持多币种"但金额字段是 INT 分、单币种假设写死在多处）。遇到这类冲突：

1. **停下并显式上报**给用户：冲突点是什么、为什么现状扛不住、波及范围多大。
2. 给出可选路径 + 代价：如"改字段类型 + 全链路迁移（大）" vs "加币种维度但先只支持人民币（小）"。
3. **让用户拍板**再往下写完善文档——不擅自选一条埋进计划里。
4. 冲突与选择结论记进完善文档「与用户确认记录」+ 未决/风险。

> 这是人工介入点。宁可多问一轮，也不要把架构级冲突偷偷藏进实现细节里。

## 三、"完善"要覆盖非功能维度 + 体验维度，不只是功能补全

只补业务分支、不看非功能和体验，改完常出慢 SQL、并发错账、或者功能对了但用户不会用。完善文档必须逐条评估（不涉及就写"无影响"）：

- **性能**：新增的关联查询/循环会不会慢 SQL？列表页加字段要不要加索引？
- **数据一致性**：跨表/跨服务的写，要不要事务？会不会出现中间态被读到？
- **幂等**：会被重复触发的操作（支付回调、重复提交、定时重试）有没有幂等键/去重？
- **并发**：抢占类操作（扣库存、领券、抢名额）的竞态怎么防？
- **用户体验**（🎩设计）：按上面必问清单 UX 12 条逐项过——加载态/空态/错误态/成功反馈/失败反馈/权限态/确认弹窗/信息层次/文案一致性/视觉一致性/移动端适配——每条都有说法，不能只写"参考现有页面"。

## 四、完成标准 —— "优化到什么程度算完"

完善文档达到下面全部才算定稿（这就是模式②的验收线，不靠主观"差不多了"）：

- [ ] 目标业务逻辑写到**能直接照做**的粒度（正向+失败+边界都有）。
- [ ] 涉及状态机的，**全分支覆盖**（新增/变更的状态与事件都画进去了）。
- [ ] 异常与边界场景**逐项有说法**（不是只写 happy path）。
- [ ] 影响面表里每条受影响功能都**和用户确认过**"是否同步改 + 改什么"。
- [ ] 非功能五维（性能/一致性/幂等/并发/用户体验）都评估过。
- [ ] UX 各状态（加载/空/成功/失败/权限/网络异常）**逐项有设计方案**，不只是写"toast 提示"。
- [ ] 与现有架构的冲突（如有）已上报并有用户拍板结论。
- [ ] **三顶帽子复核**：每项决策都经过了产品/项目/设计三个视角的审视，没有哪个视角被遗漏。

## 五、影响面的可追踪链接（让"影响哪些功能"能被反查）

完善文档影响面分析表里，每条"需同步修改"的受影响功能，用 **`[[模块id]]`** 标注对应模块。这个 id 是贯穿链条的 key：

```
完善文档.影响面[[coupon]] → 计划文档.同步改动步骤(引用 [[coupon]]) → 模式③收尾核对 [[coupon]] 是否真被改
```

这样模式③收尾时能拿着 id 逐个反查"这些被点名的模块，实际动了吗"，而不是凭印象。这是"轻量可追踪"——用已有的模块 id 串起来，不引入额外的编号系统。

## 六、第二步：实施计划文档要包含的章节

计划文档（`docs/business-logic/plan/<日期>-<业务名>-实施计划.md`）不是只列几步就完了。按 `assets/计划文档.template.md`，至少含：

- **目标与范围**：对应完善文档的"目标业务逻辑"，并**引用完善文档路径**（`../improve/<那份>.md`）。
- **任务拆解 + 依赖顺序**：分步，标出哪些步骤有先后依赖（如"先加字段再改接口再改前端"）、哪些可并行。**不估工时**——AI 执行没有 hour 概念；改用**复杂度/风险等级（低/中/高）**标注哪些步骤要格外小心。每步末尾标注视角标签（🎩产品/🎩项目/🎩设计），确保三个视角都有对应步骤落地。
- **各端改动**：每步落到哪个端、哪个接口。
- **UX 实现清单**（🎩设计）：从完善文档的 UX 评估中拆出具体的前端实现任务——每个页面的加载态/空态/错误态/成功反馈分别用什么组件实现、确认弹窗加在哪个操作上、文案统一改哪些页面、移动端适配检查哪些点。这是独立任务，不和"改业务逻辑"混在一起。
- **受影响功能的同步改动**：把影响面里 `[[id]]` 标了"需同步"的，落成具体步骤。
- **验证与验收**：对应完善文档目标逐条给验收方式（跑什么、看到什么算过）；标注该用哪些验证层级（分层定义见本技能 `references/validation-levels.md`，内联）。**UX 验证单独列**：在真机/浏览器上逐个状态走一遍（加载→空→正常→错误→权限），截屏或录屏确认。
- **风险与回滚预案**：这步万一失败/做错，怎么退（如"在 worktree 里做，坏了直接丢弃"、"迁移脚本先备份"）。
- **末尾固定一句**：`同步到项目白皮书的 md 文档对应的业务逻辑中`——提醒执行完回写模块文档 + 更新根白皮书状态。

可用本技能 `references/writing-plans.md`（内联）的方法打草稿，最终存进 `plan/`。

## 七、实施计划写完后：对抗式审查门（必过，进执行前最后一道闸）

计划文档落盘 ≠ 可以执行。**在告诉用户"可以执行"之前，必须让挑刺者（本技能内置的 adversarial-reviewer，见 `references/adversarial-reviewer.md`）审一遍，双方相互说服，才算过关。** 目的是把"自以为是"挡在执行前：逻辑矛盾、想当然的前提、边界会崩的点、有更便宜路径的地方，都在这道闸里暴露。

### 审查对象与输入

- **主攻**：实施计划文档（`docs/business-logic/plan/<日期>-<业务名>-实施计划.md`）
- **背景**：同模块的完善文档（`docs/business-logic/improve/<那份>.md`）——挑刺者拿它判断计划有没有忠实于已确认的需求，以及需求本身的坑。
- 挑刺者输出固定格式：每条 `①问题描述 ②严重程度（致命/高/中/低） ③修复建议`，按严重程度降序。定义见 `references/adversarial-reviewer.md`。

### 轮次协议：最多 2 轮相互说服

子智能体是**无状态**的，每次调用都是全新上下文——"相互说服"必须靠**把辩论历史带进下一轮 prompt** 实现，不能指望挑刺者记得上一轮。

**R1 · 挑刺**：用 `references/adversarial-reviewer.md` 的正文当子智能体 prompt，喂它①计划文档路径 ②完善文档路径（背景）③明确要求"按①/②/③格式输出、按严重程度降序、臆想出来的漏洞比没有更糟"。

**辩护与修复（写计划者逐条处理，三顶帽子视角）**：收到 findings 后每条必须表态，不得跳过：
- **接受并修复**：问题成立 → 改计划文档，记 `已修复：<具体怎么改的>`
- **反驳**：问题不成立（误读 / 臆想 / 计划现有机制已覆盖 / 修复代价远大于收益且不构成风险）→ 写 `已反驳：<证据与理由>`，要能指出计划里哪里已覆盖、或为什么代价大于收益，不许空话。
- 铁则：**不接受也不反驳就默认接受**。没有"留到执行时再看"。

**R2 · 复核**：把**修复后的计划 + R1 全部 findings 及各自的修复/反驳记录**打包再用 `references/adversarial-reviewer.md` 派一次挑刺子智能体，指令：
- 逐条看过修复与反驳，明确回答：`接受`（理由）或 `继续质疑`（具体哪点仍不成立、为什么）。
- 禁止原地复读：同样的论点不许换皮再说一遍，必须回应写计划者的反驳。
- 可提出**新发现**的问题（修复可能引入新坑，例如改了 A 忘了 B）。

**收敛判定**（R2 结束后写计划者裁断）：

| R2 结果 | 判定 |
|---------|------|
| 无新问题 / 全部接受 | **通过** → 可宣告"可以执行" |
| 只剩 中/低 且写计划者能给接受风险的理由 | **带条件通过** → 列「已知风险清单」随报告给用户 |
| 有 致命/高 且说服不了（修不掉也驳不倒） | **不通过** → **不宣告可执行** → 回到质询（`references/grill-with-docs.md`）/ 用户拍板，改完**重新从 R1 走** |

### 权责：谁让谁、谁有最终决定权

- 挑刺者是**同级审查者，不是审批者**，没有一票否决权。
- **相互说服**的含义：哪边论点更好哪边让。写计划者论点好（反驳成立）→ 挑刺者接受；挑刺者论点好（问题真）→ 写计划者修复。
- 写计划者（代表已与用户确认过的需求）对非致命分歧有**最终决定权**，但必须给理由并计入审查记录；挑刺者对致命问题的质疑权重最高，修不掉就得上报用户。

### 成本护栏

- **硬上限 2 轮**（R1 + R2），绝不第 3 次调用挑刺者。2 轮后仍有非致命分歧 → 写计划者裁断 + 记「已知风险」，往下走。
- 挑刺者在细枝末节上空转（例如死咬文案措辞）→ 写计划者可把这类降级为"已反驳"，不消耗 R2 弹药。
- 挑刺者没按 `①/②/③` 格式输出 → 要求它重出，别带着散装问题往下走。
