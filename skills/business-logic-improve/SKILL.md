# 业务逻辑 · 完善与优化（Improve）

把某块业务逻辑补全或按新需求改造。**先确认需求再出计划。** 产出三份文档：完善文档（需求分析 + 影响面 + UX 方案）+ 实施计划文档（分步计划 + 风险 + 验证）+ 对抗式审查记录（挑刺→辩护→复核的完整凭据）。

> 本文件是骨架。可执行细节在 `references/` 下（**全部内联，无外部依赖**）：
> - `references/mode2-improve.md` —— 三顶帽子方法论、必问清单（含 UX 12 条）、非功能五维、架构冲突上报、完成标准、对抗式审查门协议
> - `references/module-doc-spec.md` —— 单模块文档写作规范（补现状时用）
> - `references/grill-with-docs.md` —— 与用户质询确认需求的方法（内联自原技能）
> - `references/adversarial-reviewer.md` —— 对抗式审查子智能体（内联自原 agent 定义，用作子智能体 prompt）
> - `references/writing-plans.md` —— 写实施计划草稿的方法（内联自 superpowers:writing-plans）
> - `references/business-logic-extractor.md` —— 从源码抽纯业务逻辑的方法（内联自原技能，可选辅助）
> - `references/validation-levels.md` —— 验证分层 L0-L4（内联自 mode3-execute）
>
> 模板在 `assets/`：`完善文档.template.md`、`计划文档.template.md`

## 先进路由判断

进来先判断这个任务**是否归我管**：

| 情况 | 行动 |
|------|------|
| 项目**还没有**白皮书或目标模块根本没文档 | 先引导用户用 `business-logic:init` 建档，再回来 |
| 模块文档非 `已核对` | **先补现状**（用 `references/module-doc-spec.md` 把模块文档补齐到可信任），再谈优化 |
| 模块 `已核对`、用户要"完善/优化/改" | **走我的主流程**（见下） |
| 用户只是照已有计划文档写代码、没有新决策需要做 | **不是我管** → 提示用户用 `business-logic:execute` |

**前置依赖**：动手前**必须先读**该模块的 `docs/business-logic/<模块>.md` + 白皮书里它的影响面。这是模式①的产出物，是我的输入。

## 核心方法论：三顶帽子思考法

每个决策点同时从三个专业角色视角审视，不是分步走而是**同时问**：

- 🎩**产品经理**：业务对吗？正向/失败/边界都覆盖了吗？和现有功能矛盾吗？存量数据怎么办？
- 🎩**项目经理**：风险在哪？怎么回滚？依赖顺序是什么？怎么验证？
- 🎩**设计师**：用户操作几步？加载/空/成功/失败/权限/网络异常每个状态都有方案吗？

详细方法 + 必问清单 + UX 12 条 + 非功能五维 + 三顶帽子复核表，都在 `references/mode2-improve.md`。

## 主流程：两步产出

### 第一步：确认需求 → 完善文档

1. **与用户确认**（用 `references/grill-with-docs.md` 的质询法）：按 `references/mode2-improve.md` 的输入/输出契约喂给它（现有文档+代码+一句诉求+术语），逐条逼出明确决策。走**必问清单**（目标行为、历史数据/迁移、停机/灰度、影响面、非功能、权限与端、UX 12 条），别只问"改成什么样"。质询细节照 `references/grill-with-docs.md` 执行。
2. **遇到需求与现有架构冲突**（如多币种 vs INT 金额字段）→ 停下显式上报、给路径+代价、让用户拍板，不硬来。
3. **写完善文档**：按 `assets/完善文档.template.md` 在 `docs/business-logic/improve/` 生成，文件名 `<日期>-<受影响业务名>-<需求概述>.md`。必含：动机 → 原有 → 目标 → **需求决策清单** → **非功能评估** → **影响面分析（每条 `[[模块id]]` 标注）** → 架构冲突 → 确认记录 → **UX/UI 每页面逐状态设计方案** → 三顶帽子复核表 → **完成标准自检**（全打勾才定稿）。

### 第二步：据完善文档 → 实施计划文档

4. **写计划文档**：按 `assets/计划文档.template.md` 在 `docs/business-logic/plan/` 生成，文件名 `<日期>-<受影响业务名>-实施计划.md`。**引用上一步完善文档路径**；含任务拆解+依赖顺序+**风险等级（不估工时）**、各端改动、UX 实现清单、受影响功能同步改动、验证层级（分层定义见 `references/validation-levels.md`）、**风险与回滚预案**；**末尾固定写**：`同步到项目白皮书的 md 文档对应的业务逻辑中`。可用 `references/writing-plans.md` 的方法打草稿。
5. **对抗式审查门（必做，进执行前最后一道闸）**：用 `references/adversarial-reviewer.md` 的内容派子智能体挑刺实施计划文档（同模块完善文档作背景）。最多 2 轮相互说服——R1 挑刺 → 写计划者逐条「修复/反驳」；R2 拿修复后计划 + 反驳记录让挑刺者复核。无新问题→通过；致命/高未解→**不宣告可执行**，回到质询让用户拍板，改完重走 R1；只剩中/低→列「已知风险清单」带条件过。辩论全程落盘 `docs/business-logic/plan/<日期>-<业务名>-审查记录.md`。细则见 `references/mode2-improve.md` 第七节。
6. **交接**：报告审查结论（挑了什么刺 / 修了什么 / 反驳了什么 / 剩余风险）与结论（✅通过 / ⚠️带条件 / ❌不通过）。**只有通过或带条件通过**才问用户是否进执行（引导到 `business-logic:execute`）；不通过则说明卡点、请用户拍板。

## 影响面可追踪

完善文档影响面分析表里，每条"需同步修改"的受影响功能用 **`[[模块id]]`** 标注。这个 id 贯穿到计划文档 → 执行 → 收尾核对，让"谁被影响"能被反查。

## 铁律速查

- **先路由**：没有白皮书先建档；模块非 `已核对` 先补现状。
- **先进 reference**：`references/mode2-improve.md` 里才是可执行细节。
- **三顶帽子**：每个决策同时问产品/项目/设计。
- **先确认再计划**：质询（grill-with-docs 内联）→ improve 文档 → plan 文档，不跳过。
- **架构冲突上报**：用户诉求和技术栈打架时停下让用户拍板。
- **文档写全**：完善文档含 UX 每页面每状态设计 + 非功能五维评估 + 完成标准自检。
- **写完计划必过对抗式审查门**：adversarial-reviewer（内联）挑刺 → 相互说服最多 2 轮；致命/高未解不得宣告可执行，回用户拍板。
- **自包含**：grill-with-docs / adversarial-reviewer / writing-plans / business-logic-extractor / 验证分层都已内联在 `references/`，运行本技能不需要安装任何外部技能或智能体。
