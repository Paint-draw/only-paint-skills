# 业务逻辑 · 漏洞猎人（Hunt / 审计查漏）

对某个业务模块（或全项目）做**只读审计**：以文档为规则清单查代码（没实现/实现偏了），再以代码为准反查文档（多了什么没写），最后按漏洞清单兜底，交付一份**带证据链、分级、修复建议**的审计报告。**只查不改**。

> 本文件是骨架。可执行细节（门禁必问、规则清单与取证协议、六类检查项、证据卡片、分级口径、自查清单）在 `references/hunt-details.md`；交付报告模板在 `assets/业务逻辑审计报告.template.md`。全部自包含，不依赖外部技能/智能体。

## 家族分工：我是哪一环

| 用户的诉求 | 该走谁 |
|---|---|
| **查漏洞 / 审计 / 找缺口 / 核对代码与文档** | **本技能** |
| 完善/优化/改造业务逻辑，出完善文档+计划 | `business-logic-improve` |
| 手上有计划文档，把计划落地成代码 | `business-logic-execute` |
| 项目没有白皮书体系，要建档/查漏补缺 | `business-logic-init` |
| 把现状抽成面向业务方的需求文档 | `business-logic-reqdoc` |

边界：本技能**只查不改**——不给代码打补丁、不替用户拍板。发现的真缺口在报告里给修复方向；是否要修、要不要我补文档，一律在交付时问用户。用户说"顺便修了吧"→ 引导先用 `business-logic-improve` 把修复变成完善文档+实施计划（大缺口尤其要）；用户说"把文档补上吧"→ 得到点头后按白皮书写作规范补模块文档并回写总览状态。

## 为什么是这几条铁律（踩了报告就不可信）

1. **范围不清不撒网。** 审计范围（模块、端、是否含安全深度、用户已知问题、输出落点）没确认就整仓乱扫，产出必然又浅又不可核对。动笔前至少跑完「范围门」（见 §0）。
2. **规则清单没建就对照，等于凭感觉挑刺。** 先把文档/需求/计划里该模块的**每条规则**抽成清单（含出处），对照才有方向；没建清单就扫代码，只会捡到表面问题漏掉深层规则缺口。
3. **证据是唯一货币。** 每条发现必须能落到 `文件:行`/符号/接口/迁移/表，并指出它违反或缺失的文档出处。区分「已证实」（代码直接证明）与「疑似待确认」。**没有证据的发现不许写进正文**——宁可少报。
4. **不一致不猜不改不抹平。** 前端文案 vs 后端规则、文档 vs 代码、计划 vs 实现打架时，把「双方说法 + 证据 + 推荐口径」列给用户拍板，不许擅自按一侧改写、不许把矛盾描述成一致。
5. **代码有文档无 ≠ 代码错，但必须抓到。** 这类是「文档同步缺口」，单列一节；是否当场补文档要问用户（审计不改文档，避免边查边改互相污染）。
6. **分级不是装饰。** 严重度必须给出业务影响理由（谁会被影响、钱/数据/流程会不会坏）。没有资金/数据泄露级影响的不得标「致命」；把什么都标严重 = 报告失效。
7. **自查不过不收尾。** 证据抽查、正/反向覆盖、分级复核、模板完整、待确认带证据——全过才算交付。

## 工作流（范围门 + 七步）

### 0｜范围门（先于一切）
- 一次一问，先给推荐答案+理由；**代码能答的不问**（先查再问）。
- 最小边界集：① 审计对象（单模块 or 全项目；模块名/子功能逐项列）② 端与角色（前台/后台/服务端；普通用户/管理员/供应商）③ 深度选项（要不要安全面扫描、要不要逐接口对账）④ 已知问题（用户手里已有的怀疑先说出来）⑤ 输出落点（默认 `docs/business-logic/audit/`，目录不存在先问）。
- 用户催稿/说别问了：说明省略的后果，但**范围门至少过一遍**；用户不在场就停下等回复，不把一堆未拍板项攒到交付后甩给用户（免问牌不存在）。

### 1｜拉基准：规则清单
- 读：模块文档（`docs/business-logic/<模块>.md`，重点「后端处理逻辑与业务规则」节与状态流转）、相关需求文档（`docs/business-logic/requirements/`）、实施计划（`plan/`）、`业务逻辑白皮书.md` 模块行、接口契约对齐矩阵。
- 产出「规则清单」：每条 = 规则一句话 + 触发/守卫 + 出处（文档章节）+ 是否已核对 状态。文档是"草稿"的，如实标注，规则清单更要以代码为主核对。

### 2｜正向核对（文档 → 代码）
- 规则清单逐条找实现证据：定位服务/控制器/校验/迁移/前端。判定：**已实现 / 部分实现（缺什么分支写清楚）/ 未实现 / 实现不一致**。
- 规则间的隐性要求也查：额度上限除了入口校验，消费路径/并发路径有没有第二个口子；状态机除了主流程，定时任务/回调/回滚分支有没有绕过守卫。

### 3｜反向核对（代码 → 文档）＋文档同步缺口
- 换方向扫：服务方法、控制器端点、实体与迁移约束、Job/后台任务、前端页面/按钮/写死文案里的业务行为。
- 代码有、文档没写的 → 「文档同步缺口」候补；文档有、代码没对应的已在 §2 记下。
- **核对完必须各写一行「覆盖结论」**（细则 §3/§4）：正向=核对 N 条规则，X 已实现 / Y 部分 / Z 未实现或不一致，Z=0 也要写检索位置；反向=扫了哪些文件、检出 M 条文档同步缺口、未检出方向的证据一句。不许用空口「已核对/未见」收尾。

### 4｜清单兜底（六类）
按 `references/hunt-details.md` §5 的六类检查项过一遍（规则缺口 / 权限越权IDOR / 数值限额 / 状态机流程 / 并发事务幂等 / 安全面）。每类都有取证位置与典型漏网，**对照着查而不是背概念**。

### 5｜取证与分级
- 每条发现填「证据卡片」（细则 §6）：业务事实 / 代码证据 / 文档出处 / 触发路径（谁能怎么触发，含前置条件）/ 影响 / 修复方向 / 严重度 / 状态。
- 分级口径见细则 §7：致命（资金损失 / 大范围数据泄露 / 全线越权 / **核心业务主线整体不可用或闭环断裂**）/ 高 / 中 / 低 / 提示（改进项、文档同步缺口）。**无业务影响理由不得标高与致命。**

### 6｜报告（按模板）
- 输出：`docs/business-logic/audit/YYYY-MM-DD-<模块>-业务逻辑漏洞审计报告.md`（目录不存在先问落点；仓库无白皮书体系则问存放处）。
- 结构照 `assets/业务逻辑审计报告.template.md`（报告紧凑化：范围门与规则清单写小结、不贴清单全文，正文尽量 ≤250 行）：审计范围 → 发现清单（按严重度降序）→ 文档同步缺口 → 结论与优先级 → 给用户的待确认问题 → 审计过程记录。
- 报告含代码标识（文件:行/符号/接口/表/迁移）——本技能与 reqdoc 相反：**没有精确证据定位就是废报告**。

### 7｜收尾：交付并问两件事
- 汇报五件事：① 审计范围与覆盖 ② 发现数与致命/高计数 ③ 与文档的不一致点及处置 ④ 待确认问题（带证据） ⑤ 报告路径。
- **结尾问两件事**：A) 是否要我修复？→ 要：引导 `business-logic-improve`（先完善/计划，再 `business-logic-execute` 落地）；B) 文档同步缺口要不要我直接补模块文档？（点头后补，并回写总览「最近更新/状态」）。
- 用户点头前不宣称审计"闭环"；报告本身写完即交付，但状态如实（初稿/已复核）。

## 范围与并行

- **单模块审计**（默认）：一次一个模块，细则 §8 的读取节奏控制上下文。
- **全项目盘点**：按白皮书模块表拆模块，每个模块走 §1-§6；能并行（子代理/多会话）就并行，各自产出后合并成总报告 + 每模块分报告。会话受限时逐模块顺序做，每模块交付一次小结，不攒到最后。
- 审计中读到明确的代码缺陷（bug）也照常记录——但它属于「已证实/疑似」按证据分级，修复一律走流程，不顺手改。
