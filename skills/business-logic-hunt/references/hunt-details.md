# Hunt 执行细则（业务逻辑漏洞猎人）

> SKILL.md 骨架的配套。把「双向核对 + 六类清单兜底 + 证据分级 + 只查不改」落到每一步可执行。

## 0. 管什么

输入：某个业务模块（或全项目）的文档与代码。输出：**业务逻辑漏洞审计报告**（含证据链、严重度、修复方向）+ 给用户的待确认问题。红线两条：
1. **只查不改**：不写/不改业务代码、不改白皮书/模块文档（补文档必须用户点头，见 §9）；但可以、也应该给出修复方向。
2. **证据为王**：正文每条发现都有精确代码定位与文档出处；「已证实 / 疑似待确认」分开；无证据=不写。

## 1. 范围门（先于一切；免问牌不存在）

### 1.1 最小边界集（动笔前至少问完，逐条记「问题→拍板答案」）
1. **审计对象**：单模块还是全项目？单模块的话子功能逐项确认纳入/排除（例：审询价时，报价、过期、通知、后台处理要不要一起）。
2. **端与角色**：前台/后台/服务端（RAG）覆盖哪些？审计视角角色（普通用户/会员/供应商/审核员/管理员）哪些要查越权？
3. **深度选项**：要不要逐接口对账（接口契约矩阵）？要不要做安全面扫描（上传/注入/信息泄露）？还是只查业务规则？
4. **已知问题**：用户手里已有的怀疑/历史发现先说出来，作为重点核验对象，但**不是唯一对象**。
5. **输出落点**：默认 `docs/business-logic/audit/`；该目录不存在或仓库没有白皮书体系 → 先问存放处。

### 1.2 质询节奏
- 一次一问，等回答再问下一个；每问先给推荐答案 + 一句理由；用户回「你定」也要复述确认。
- **代码能答的不问**：先查代码，查不出再问人（例：某模块有几个状态、哪些端点没鉴权，看代码就知道）。
- 术语冲突（文档 vs 代码 vs CONTEXT）→ 先指出再对齐。
- 用户不在场 / 演示 / 赶稿 → 停下等回复；范围没拍板只允许交「预扫描 + 待确认问题」，不许当正式报告交付。

## 2. 拉基准 · 规则清单（对照的骨架）

### 2.1 输入源
- `业务逻辑白皮书.md`：模块表行、阅读指引、覆盖总览（该模块状态：已核对/草稿）。
- `docs/business-logic/<模块>.md`：重点「后端处理逻辑与业务规则」「状态流转」「各端接口清单」「未决问题/溯源」。
- `docs/business-logic/requirements/` 相关需求文档；`docs/business-logic/plan/`、`improve/` 中该模块强相关的最近计划/审查记录（速读，防规则已拍板但正文没同步）。
- `docs/business-logic/接口契约对齐矩阵.md`（若有）：逐端点契约。

### 2.2 规则卡片（每模块 20~60 条，别贪多求全）
> 规则编号 R01…｜规则一句话（谁/何时/结果/例外）｜出处（文档章节/需求ID/计划节）｜类型（守卫/额度/状态机/联动/界面可见）｜核对状态（待核/已核）｜判定（实现/部分/未实现/不一致）

抽取要点：
- 把「前端承诺」（文案、按钮、展示、限次提示）也当规则——很多不一致是前端说了、后端没做。
- 把「隐性规则」显式化：状态守卫、幂等承诺、唯一性承诺（文档常写成业务语言，代码要找到对应约束）。
- 文档状态是「草稿」的模块：规则清单以代码事实为主核对，标注「文档草稿，可能滞后」。

## 3. 正向核对（文档 → 代码）

逐条规则找实现证据。追踪完整链路：**入口（页面/按钮/端点）→ 前端校验/门控 → 后端方法 → 业务规则/状态机 → 数据落地（迁移约束）→ 返回/通知**。

| 判定 | 含义 | 处置 |
|---|---|---|
| 已实现 | 找到完整实现，行为与规则一致 | 规则卡标 ✓，不用写成发现 |
| 部分实现 | 主路径有，缺分支（异常/边界/并发/定时） | 写清缺什么 → 通常是一条发现 |
| 未实现 | 文档写了、代码无对应（接口404/按钮未接/逻辑不存在） | 发现（类型=规则缺口），证据=检索无果+邻近证据 |
| 实现不一致 | 两侧说法冲突（阈值/守卫/门槛/口径） | 记「双方说法+证据+推荐口径」，问用户拍板；拍板前不入正文事实 |

注意：
- **同一规则的多处实现**：入口校验有、消费/扣减路径漏；管理端有、用户自服务漏；主流程有、定时任务/回调漏。全查。
- 接口对账（若深度含）：模块文档接口清单 vs 控制器路由逐条对；多出来的端点进 §4，缺的进发现。
- 前端写死文案 vs 后端规则（促销横幅、限额提示最常见）逐条对。

**正向核对结论（必写）**：结束时给一行——核对 N 条规则 → X 已实现 / Y 部分（缺什么）/ Z 未实现或不一致；Z=0 也列出重点检索位置（服务/控制器/迁移/前端各查了什么），不许只写「全部一致」糊过去。

## 4. 反向核对（代码 → 文档）＋文档同步缺口

- 从代码侧枚举业务行为：AppService/Controller 方法、实体/迁移约束、Job/后台任务、前端页面按钮/文案/状态展示、配置开关。
- 每条问：模块文档里有没有写？有→过；没有→**文档同步缺口候补**（代码有、文档无）。
- 文档同步缺口也要给证据（代码定位），并且判断其"业务显著度"——不是所有代码细节都要进文档，但**业务行为**（新状态、新规则、新入口、新限额口径）必须补。
- 输出到报告 §2「文档同步缺口」，结尾问用户是否要我补文档（§9）。

**反向覆盖结论（必写）**：结束时给一行——扫了哪些文件/端点/迁移/前端（可写数量级），检出 M 条文档同步缺口；某个方向一条没检出时，写明检索过的位置与所用检索词，不许空口「未见」。

## 5. 清单兜底（六类，逐类扫）

> 用法：每类先看"取证位置"再扫，别背概念。每类找到的进证据卡片。

### 5.1 业务规则缺口（文档没覆盖的深层逻辑问题）
- 抓：校验缺失、判定条件写反/写漏、异常分支吞掉、规则只在前端实现、超限仍放行、回退/补偿缺失。
- 取证位置：Service 方法体、Controller、前端表单校验与按钮条件、迁移约束、定时任务。
- 典型漏网：入参未校验就落库；条件只查一层；失败路径"假装成功"；文档承诺的异常表现没实现。

### 5.2 权限 / 越权 / IDOR
- 抓：分层（前台 vs 后台）隔离、[Authorize]/权限点装饰与实际检查、AdminOnly、角色-数据范围、Id 参数未校验归属、硬编码管理员/特权绕过、缓存或会话里的授权过期。
- 取证位置：Controller 特性、AppService 方法上的权限检查（ABP：CheckPermission/AuthorizationService）、查询里的归属过滤（UserId=当前人 有没有）、前端路由守卫 vs 接口直调。
- 方法：写端点清单逐个看"谁调的"；把每个带 Id 的读改删端点问一遍"换别人的 Id 会怎样"。

### 5.3 金额 / 数量 / 额度 / 数值限额
- 抓：负数/零/NaN/溢出、整数与小数类型（decimal vs double 精度）、上限与下限检查位置、检查与使用之间的 TOCTOU、额度扣减是否原子、单位换算/舍入方向（进一/四舍五入/截断）、累计与重置口径、重复扣减、免费额度与开关绕过。
- 取证位置：Dto 校验（DataAnnotations/手动）、Service 扣减/计算、价格联动更新、迁移 CHECK/默认值、前端输入限制（前端限制 ≠ 后端有校验）。

### 5.4 状态机与流程
- 抓：非法跳转（跳过中间态）、同一事件重复触发、已终态还能操作、状态条件与动作条件不一致、回滚/退回路径、超时/过期处理（定时任务 vs 读取时惰性修正是否一致）、作废/重开、通知与状态联动。
- 取证位置：状态枚举与流转方法、各 Update 方法的守卫分支、Job、前端按钮禁用条件与后端返回错误。
- 方法：列「状态 × 事件」矩阵，逐格找代码分支；文档状态机没写的格子 → 是缺口（文档或代码）。

### 5.5 并发 / 事务 / 幂等
- 抓：检查+写入不原子（先查再减/先查再插）、并发重复创建（唯一索引缺/有但被软删绕过）、批量任务重复执行（多实例/重试）、事务边界（跨表/跨服务/外部调用在事务里）、锁（乐观并发/悲观/分布式）缺失、超时与补偿。
- 取证位置：Update/Insert 方法（SaveChanges 前后有无再查）、唯一索引迁移、Job（是否防重入/分布式锁）、批量导入（预览与提交是否同一事务）、MQ/后台队列消费幂等。

### 5.6 安全面（越权之外）
- 抓：信息泄露（错误信息、日志、列表未过滤字段）、文件上传（类型/大小/魔数/路径穿越/覆盖）、注入（SQL/命令/路径）、SSRF（RAG 拉取/图片代理）、JWT/会话（过期、刷新重放）、敏感字段返回给不相关角色、XSS/CSRF（若项目有相关输入输出）、RAG：文档内容越权检索/跨租户 region。
- 取证位置：上传处理、URL 参数拼接、错误响应结构、日志记录、公开接口的返回 Dto、跨服务调用。

## 6. 证据卡片（一条发现一张，报告正文由它生成）

> 编号 H01｜标题｜类型（规则缺口/权限越权/数值限额/状态机/并发事务/安全/其它）
> 业务事实：文档/预期是什么（有出处就写）
> 代码证据：文件:行 + 符号/端点/迁移 + 关键代码摘录（≤5 行）
> 触发路径：谁能怎么触发（角色+操作序列+前置条件）
> 影响：谁受损/多少钱/多少数据/流程卡哪；写实不夸张
> 修复方向：1-2 句（不做实现细节）
> 严重度：致命/高/中/低/提示（理由必须与影响对应）
> 状态：已证实（代码直接证明，可复现于读码）/ 疑似待确认（需人工或运行验证）

## 7. 分级口径

| 级别 | 判据（满足其一） | 例子 |
|---|---|---|
| 致命 | 直接资金损失；大范围数据泄露/篡改；全线越权（任意用户/任意数据）；核心流程可被轻易绕过；**核心业务主线整体不可用/闭环断裂**（业务方最先关心的断点） | 订单金额可篡改；任何人可读全库；未登录可调管理端写接口；询价创建入口对全部目标用户必被拒、后台报价→成交 UI 全程不可达 |
| 高 | 单一/可控条件下的资金或敏感数据风险；越权范围有限但有明确受害方；核心状态机可被业务用户破坏；并发导致真实重复扣减/重复创建 | 可看他人询价详情；重复点击可超扣额度；供应商可操作他人报价 |
| 中 | 影响正确性/数据完整性但需前置条件或危害局部；明显文档-代码不一致（用户会被误导）；异常分支缺失导致流程卡死 | 关闭状态还能被编辑；导入撞键静默覆盖部分行；前端说限制 X 后端不拦（未达高危害） |
| 低 | 行为偏差/体验/边界问题，无资金数据风险 | 校验报错文案不一致；数字精度显示问题；提示信息误导 |
| 提示 | 不是缺陷但值得记录：改进项、文档同步缺口、规范性建议 | 代码有但模块文档没写的业务行为；重复代码；注释与实现不符 |

**纪律**：定级写理由；不确定取保守（同样影响面，宁可标低让用户复核，也不许夸大刷存在感）。致命/高数量少而精才可信。

## 8. 取证效率（别把上下文耗光）

- **grep/glob 先定位，read 只读关键段**：搜符号名/端点字符串/实体名，命中后再精读。
- 阅读顺序：Controller → AppService → Entity/Migration → 前端页面 → Job/配置。跳读，不逐行。
- 一条线索查 3~5 处没结果就放下，记「未找到实现（已检索 X/Y/Z）」给未实现类发现的证据。
- 全项目时拆模块，每模块独立一轮（可并行子代理）；单模块一轮控制在 60~120 分钟等效工作量内，超了就缩小范围并如实写覆盖。
- 不要在审计中途被带偏去"修复验证"：不启动服务、不改数据（静态证据足够分级为"已证实"的只限代码可直接证明的；需运行才能证明的一律"疑似待确认"）。

## 9. 自查清单与收尾（有 ✗ 不收尾）

- [ ] 范围门五问过完，「问题→拍板」记录在案；未拍板项带证据进「待确认」
- [ ] 规则清单已建（含前端承诺与隐性规则），文档草稿状态已标注
- [ ] 正向：每条规则有判定；部分/未实现/不一致都成了发现或待确认；「正向核对结论」已写（计数+检索位置，含零命中说明）
- [ ] 反向：代码业务行为对照过模块文档；文档同步缺口单列、带代码证据；「反向覆盖结论」已写（扫了哪些文件+检出数+零命中方向证据）
- [ ] 六类清单都扫过（每类结论：查了哪些位置/没发现什么，写一句，别空口"无"）
- [ ] 每条发现：证据定位 + 触发路径 + 影响 + 修复方向 + 分级理由 + 状态 齐全
- [ ] 分级复核：无业务影响理由的致命/高清零；致命/高总数为 0 要说明（不代表没审）
- [ ] 报告模板完整；过程记录诚实（读了哪些、没读哪些）
- [ ] 结尾问了两件事（是否修复→improve；文档缺口是否补文档）；没问=不收尾
- [ ] 输出路径正确；报告状态如实（初稿/已复核）；用户点头前不宣称闭环

## 10. 输出与收尾（再次强调边界）

- 交付物：`docs/business-logic/audit/YYYY-MM-DD-<模块>-业务逻辑漏洞审计报告.md`（模板见 assets）。
- 汇报五件事 + **结尾两个问题**：
  1. 发现要修吗？→ 引导 `business-logic-improve`（先完善文档+实施计划），不要当场偷改代码。
  2. 文档同步缺口要我现在补吗？→ 点头后按模块文档写作规范补，回写总览「最近更新/状态」；拒绝就留在报告里。
- 报告里的建议与用户后续行为（improve/init）形成闭环，本技能自己不开工修复。
