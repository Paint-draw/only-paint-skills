# 报告体例

读者是**甲方业务方、内测评审人**，不是写代码的人。他们关心三件事：能不能用、验到什么程度、上线前还差什么。

## 七节固定结构

| 节 | 标题 | 回答什么 |
|---|---|---|
| — | 页头 + 卡片 | 这份报告是什么、几组关键读数、结论一句话 |
| 01 | 测试范围与方法 | 多少个自动化用例、多少条端到端、多少接口调用，分账怎么算 |
| 02 | 平台运营端功能需求 | 平台侧每个功能现在能做到哪一步 |
| 03 | 协会管理端功能需求 | 管理侧同上 |
| 04 | 会员端功能需求 | 会员/移动端同上 |
| 05 | 平台底座与非功能 | 租户隔离、权限、审计、AI 网关、数据库版本、构建 |
| 06 | 覆盖质量（可选） | 负向/边界用例多少、口径是什么、哪些地方一条反例都没有 |
| 07 | 上线前风险与待办 | 分级列出外部依赖与已知缺口 |
| 08 | 测试结论 | 三到五条，每条带读数 |

端多于三个或少于三个时照此增减，但「范围 → 各端功能 → 底座 → 覆盖质量 → 风险 → 结论」这个顺序不要变：先讲验了什么，再讲验到哪，再讲验得有多狠，最后讲还差什么。

## 功能条目怎么写

编号 `P01`（平台）、`A01`（管理端）、`H01`（会员端）、`S01`（底座）。渲染器会把两位编号自动套等宽字体。

每条四列：**编号 / 功能 / 需求说明 / 验证**。

写「需求说明」的三条规矩：

1. **只写现在能做什么、边界在哪**。例：「缴费登记（已缴清或超额拒登、登记加行锁防并发超收）」。
2. **不写决策沿革**。「经讨论决定」「按甲方要求」「暂定」这类话不进报告——它们属于台账，不属于交付物。产品取舍写「暂不提供」即可。
3. **不写实现细节**。不写类名、接口路径、表名；只有配置键（如 `sai.demo.enabled`）和业务口径（如「已缴清拒登」）值得出现，因为评审人要拿它去验收。

「验证」列只有三种正当取值：

- `<span class="tag ok">通过</span>` —— 有证据，且证据支持「通过」；
- `<span class="tag warn">部分通过</span>` —— 主链通了，但某条支路没验（在括号里写清哪条）；
- `<span class="tag gray">未走查</span>` —— 没证据。

**没有证据就写「未走查」。** 上一版报告最典型的错误，是把手写的「UI 走查 40 页」原样留了三轮，而实际上谁也没再走过。

## 数字怎么来

- 页头日期、环境版本（数据库迁移号、框架版本）**现读**，不沿用上一版。
- 卡片与 01 节的数字全部来自 `test/evidence.json`，用 `{{tests.total}}` 这类占位符引用。
- 确实要手写的数字（比如「接口矩阵 146 次调用」这种由多个脚本拼出来的合计数），卡片上必须带 `source` 字段写明出处，否则 `build_report.py` 拒绝出报告，并在页脚「人工读数」里列出来。
- 只认实测。同一份报告里，「363 个用例全部通过」和「UI 40 页全部通过」不能并列——前者有 surefire 文件，后者没有。

## 覆盖质量怎么写

用例数只说明「跑了多少」，不说明「验得有多狠」。有一节专门讲这个，放在**风险节之前**：

```json
{"no": "06", "title": "覆盖质量", "blocks": [{"type": "quality"}]}
```

（编号按你那份报告的实际情况排，插在风险节前面即可。）

`quality` 块的数字全部取自 evidence，不手写。它固定回答五行：负向用例多少、边界用例多少、统计口径是什么、有多少测试文件一条负向断言都没有、有多少疑似陈旧报告。

写这一节最容易犯的错，是把「未统计」读成「没有」。口径没登记就照实写「未统计」，别填 0。

## 风险表怎么写

四列：级别 / 事项 / 说明与建议。级别只有高、中、低。

默认要检查的外部依赖清单（有就进表，没有就说明为什么没有）：

- 支付通道（是否模拟支付、退款与对账）
- 短信（是否 mock、验证码是否回显、频控）
- 演示数据开关（`demo.enabled` 是否会在生产误开）
- AI 供应商与模型（真模型还是 mock、密钥从哪来、单价与毛利）
- 文件存储（本地磁盘还是对象存储、备份）
- 限流存储（单实例内存还是 Redis）
- 鉴权与令牌（有效期、密钥注入方式、能否撤销）

写风险时只写**上线前必须做什么**，不写背景故事。已经改好的风险要删掉——风险表留着过期条目，比少写一条更坏。

## 结论怎么写

三到五条，每条一个读数配一句判断：

> 后端 363 个自动化用例全部通过（46 个测试类，0 失败 / 0 错误 / 0 跳过），覆盖……

最后一条给出总体判断，并说清风险集中在哪一类（通常是外部依赖，而不是代码）。
