# 测试报告生成器（test-report-html）

## 交付什么

两样东西，缺一不可：

1. **`test/` 目录**：脚本、结果、证据、叙事集中存放，进版本管理。
2. **一份单文件 HTML**：内联样式、可打印、无外链，拿到就能发人。

核心是**两段式**：

```
测试报告文件 / 运行时结果  ──collect_evidence.py──▶  test/evidence.json   （机器读数）
                                                          │
报告叙事 test/report.json（人写，数字用 {{占位符}}）────────┴──build_report.py──▶  HTML
```

分两段的原因很实际：读数天天在变，叙事几乎不变。混在一起写，就是每次都要手抄一遍数字——而上一次手抄留下的「69 个用例」「Flyway V17」在原处挂了三个月没人发现。占位符 + 校验就是为这件事设的闸门。

## 五步工作流

### 1. 探明证据在哪

先看项目有没有 `test/`，再看框架产物：

```bash
python <skill>/scripts/collect_evidence.py --project .
```

没有 `test/` 就先铺：

```bash
python <skill>/scripts/init_test_dir.py --project .
```

它只补缺不覆盖——已经改成本项目用的脚本不会被冲掉。

### 2. 补齐缺的读数

`collect_evidence.py` 的输出里，`warnings` 会告诉你哪些地方空着：没有报告文件、报告过期、有失败。这时回去补跑，而不是在报告里回避：

- 自动化用例没跑 → 跑一遍，报告文件自然出现；
- 接口/端到端没证据 → 用 `test/scripts/` 里的两个骨架写脚本跑一遍；
- 负向覆盖没读数 → 统计一次 `test/results/negative_coverage.json`（口径见 `references/test目录规范.md`）。**没有这份就不算补完**，报告里的「通过」会分不清是正例通过还是拒绝通过；
- 出现「疑似陈旧报告」告警 → 多半是已删测试类的残留产物，清掉或加 `--exclude-stale`，别让它抬高用例数；
- 确实来不及验的模块 → 报告里写「未走查」，不许写「全部通过」。

### 3. 写 `test/report.json`

照 `references/报告体例.md` 的七节结构写叙事。数字一律用占位符：

```json
{"value": "{{tests.total}}", "label": "后端自动化用例全部通过", "style": "accent"}
```

确实要手写的合计数（例如多个脚本拼出来的「接口矩阵 146 次」）必须带 `source`，否则第 4 步会直接报错。字段说明见 `references/test目录规范.md`。

写之前先把页头的**日期**和**环境版本**（数据库迁移号、框架版本）现读一遍——报告里最容易过期的就是这两处。

### 4. 生成并校验

```bash
python <skill>/scripts/build_report.py --project .            # 默认写 docs/internal-test-report.html
python <skill>/scripts/build_report.py --project . --check    # 只校验
```

报错只有三种，都是真问题，不要绕：

| 报错 | 含义 | 处理 |
|---|---|---|
| 占位符在证据里找不到值 | 证据缺项或占位符拼错 | 补跑测试，或改占位符 |
| 卡片用手写数字但没有 source | 无法追溯 | 改成占位符，或写明出处 |
| 缺少 report.json / evidence.json | 顺序错了 | 先 collect 再 build |

### 5. 交给用户看之前自查

- 打开 HTML 看一遍排版：卡片数字、表格换行、两栏是否挤。
- 抽查两条结论，回到 evidence 里对一下数字对不对。
- 风险表里有没有已经改好的旧条目（删掉）。这是上一版报告最容易残留的东西。

## 铁律

- **数字只来自证据。** 手写数字要么有 `source`，要么不写。
- **「通过」不等于「正例通过」。** 越权被 403 也是通过。负向用例要单独计数，否则报告会让业务方以为每条通过都是功能正常。
- **没证据就写「未走查」。** 「全部通过」是一种断言，不是鼓励用语。
- **只写现在怎么跑、边界在哪。** 决策沿革、谁拍板、讨论过程一律不进报告——那些属于台账。
- **日期和版本现读。** 沿用上一版是这份文档最常见的失效方式。
- **失败要落盘。** 端到端脚本里 try/except 吞掉的失败，会在报告里变成一句谎。

## 文件指针

| 想了解 | 读 |
|---|---|
| 七节结构、功能条目怎么写、风险怎么分级 | `references/报告体例.md` |
| 各框架报告在哪、为什么只数 `<testcase>` | `references/证据来源.md` |
| `test/` 布局、`evidence.json` / `report.json` 字段 | `references/test目录规范.md` |
| 端到端脚本骨架 | `assets/harness.py` |
| 角色 × 接口冒烟骨架 | `assets/smoke_matrix.py` |

## 不做什么

- 不跑测试、不改业务代码：这一步只吃已有证据。
- 不写测试用例：用例怎么写是各项目自己的事。
- 不把报告推到任何外部服务。
