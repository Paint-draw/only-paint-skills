# 技术文档体例

> 这份文件只管**写法**，不管内容。内容归各文档自己。

---

## 一、读者与目标

读者两类：

1. **没接触过本项目、来学这套实现的人**；
2. **作者自己**，回溯「当初为什么这么设计」。

⇒ 每篇只回答三个问题：**系统现在怎么跑** · **为什么这么设计** · **这块功能怎么实现**。

**推论**：文档里出现的每一句，都必须是「不懂本仓历史的人读了也能懂」的。凡是需要先补一遍本仓编年史才看得懂的话，都属于越界。

---

## 二、写什么（六类，缺一类就是没写全）

| # | 写 | 具体指 |
|---|---|---|
| 1 | **机制链条** | 请求从哪进、经过哪些层、每层做什么、**层间传的数据长什么样**、失败时走哪条路 |
| 2 | **设计理由与取舍** | 为什么选 A 不选 B；A、B 各自的代价是什么 |
| 3 | **新旧做法对比** | 旧做法是什么 → 它的**结构性缺陷**是什么 → 新做法怎么解掉 |
| 4 | **被否掉的方案** | 否掉了什么、为什么否（只写**理由**，不写探索过程） |
| 5 | **证据强度** | 实测读数与推断**分开写**；没取证的**明写「未核」** |
| 6 | **代码锚点** | 用**符号名**（`path::symbol`）定位；行号只作粗略参考，并声明它会漂 |

---

## 三、不写什么（五类 —— 不是不该记，是**记错了地方**）

| # | 不写 | 它的家 |
|---|---|---|
| 1 | **日期锚与开发批次**：`（2026-10-08 追加）` · `本批` · `本轮改造 / 本次交付` 这类**开发批次语义** · `收口态` · `（最新）` | `git log` / 台账 |
| 2 | **交付读数**：提交 sha · 测试计数沿革（`215 → 227`）· 部署与 reload 时间戳 · 真库行 id · 「已部署 / 已上线 / 已过验收」 | 台账 |
| 3 | **订正注与订正沿革**（「原文如此，已订正为…」） | 台账 |
| 4 | **台账指针**：`N233` 这类编号 · 「见总账 §X」 · 计划 / spec 文件名 | 台账 |
| 5 | **单 `★`** —— 只保留 `★★` 标承重点 | —— |

**为什么**：技术文档里读到它们，学的人得先补一遍本仓编年史，才看得懂一句设计。而这些内容在台账与 `git log` 里**一字不少**，技术文档重复一遍只会两边都可能过期。

**推论**：「改了哪一天、第几批、过了哪些测试」**一律不写**；但**「旧做法有什么结构性缺陷」要写**——那是设计理由的承重半边。

**边界**：`本轮 / 本次` 本身不是禁词——「该键本轮第一次请求的时刻」「本次返回的行数」都是合法技术表述。禁的是它们指**开发批次**（本轮改造、本次交付、本次验收）时的用法。

## 四、形状

1. **五要素**：每个主题写全——有什么方法 / 实现什么 / 解决什么问题 / 优缺点 / **原来怎么做的、哪里不好**。
2. **三块收尾**：每篇都要有独立的 **已知的粗糙处** · **被否掉的方案** · **行为变更** 三块（某一类确实没有，就写「无」，不留空白）。
   **注意**：已有编号的块保持原编号、不搬位置——例：某篇的「被否掉的方案」住在 `§15.1`、「行为变更」住在 `§15.3`，就留在那里，**不挪到文末**。
   （本条与下条冲突时，**编号稳定优先**。）
3. **索引表只列** `# / 主题 / 位置` —— **不写「共 N 个」**、不写状态、不写追加日期。
   （索引表写死数量，正文一增删就对不上；不写数字，这个坑就不存在。）
4. **章节编号稳定**：`§N` 与 `§N.M` **不重排、不合并**——代码注释、SQL 迁移文件与台账都可能按这些编号指路。
   正文可以整段重写，**编号是接口**。
5. **`未核` 保留**：它说的是「这条我们没取证」，属于**现状的诚实**，不是历史。
6. **代码锚点写法**：`path/to/file.py::symbol` 优先；非给行号不可时，在同一处声明抽取点且说明会漂。

---

## 五、样例（同一段文字，改前 → 改后）

**改前**（技术事实 2 句，交付账 5 行）：

> ★ 落地状态（如实记 · 2026-10-08 收口）：已实施 · 已过统一验收 · 已部署。
> - **提交**：graph-service 写侧 `de0b2f7`（另两轮修复 `a3b1e08` / `3ddcd5a`）· agent-service 读侧 `6ec9fdd`
> - **测试**：graph-service 全量 **215 → 227**；agent-service 全量 **324 → 328**
> - **真 Redis 往返已实测**：写入 **579** 字节 → 读回**逐字相同**、非 ASCII 无损、`TTL=599` 生效
> - **部署**：`pm2 reload silu-graph-service`（`pm_uptime` 16:37:02 晚于被改文件 16:28:15）…
> - **真实对话端到端 —— 已验证（2026-10-08 17:28）**：真库 `eval_live_sample` id=**82** …

**改后**（技术事实一条不丢，交付账全去）：

> **这套中转为什么可信**：两侧 `put_trace` / `get_trace` 用真 Redis 往返实测过——写入 → 读回**逐字相同**、
> 非 ASCII 无损、`TTL` 生效 ⇒ 排除了「两侧 `redis_url` 不同 / key 写错 / 编解码丢字」这三类**静默失效**。
>
> **端到端为什么可信**：真登录跑一次 8 跳对话，落库的 `calls` 长度 = `retrieval_calls`、`trace_source = forwarded`
> ⇒ 三件事同时成立：跨过了事故断点 · **实际 = 声称**（未被截断）· 确实是从 Redis 读到的，不是回放。
> （读失败会退化成 `replay` ⇒ `forwarded` 这个值本身就是判据。）

注意改后做了什么：**把「哪天、哪个提交、几次测试」换成了「验到了什么、排除了哪几类失效」**。前者会过期，后者是设计事实。

## 六、完整文档的骨架

```
# <模块> 实现

> 这份文档讲什么 / 不讲代码 / 文末三块

## 〇、一页概览
<从入口到出口的 ASCII 链路，含失败与降级旁注>
**一句话**：……

## 一、<机制主题>（按链路顺序）
### 1.1 <子主题>
（方法 / 实现什么 / 解决什么问题 / 优缺点 / 原来怎么做、哪里不好）

……

## 已知的粗糙处（如实列出）
## 被否掉的方案
## 行为变更
## 附：速答卡（可选，口述用）
```

章节标题应是**机制名**（「全局融合」「出站守卫」「凭证与加密」），不是文件名（「service.py 说明」）。

## 七、术语与语气

- **结论先行**：每节第一句就回答「这里做了什么」，再展开。
- **短句**：一句话只承一个判断。长从句堆叠会让承重点消失。
- **表格优先**：对比、参数、失败分支、护栏层次，先想能不能表格化。
- **加粗只给承重点**：一段里加粗超过三处，等于没有重点。
- **不写「我们认为」「应该是」「大概」**：要么有证据，要么写「未核 / 推断」。
- **术语首现给定义**：一句话即可，不要假设读者知道你们的内部叫法。
- **数字要可复算**：写「实际值 + 默认值 + 覆盖来源」，不要只写一个孤零零的数值。

---

## 八、边界

- 本文件**不规定内容**——某主题讲多深、举什么例子，由该文档自己定。
- 台账**不受本文件约束**——它的职责就是记变更史、交付读数与裁定沿革。两边的分工：**台账回答「这件事经历了什么」，技术文档回答「系统现在怎么跑、为什么」。**
