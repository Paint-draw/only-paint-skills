# 取证指南

> 这份文件只管**怎么读代码、怎么确认事实**，不管怎么写。写作规范见 `体例.md`。

---

## 〇、先建证据表，再动笔

动笔前维护一张表。每条准备写进文档的断言占一行：

| 断言 | 证据（命令 / 代码路径 / 输出） | 等级 | 锚点 |
|---|---|---|---|
| 限流窗口长度 60s | `LITELLM_RATE_LIMIT_WINDOW_SIZE` 未设，默认 60 | 实测 + 读码 | `parallel_request_limiter_v3.py::_PROXY_MaxParallelRequestsHandler_v3` |
| 检索两路不在库内融合 | 两路各自返回 list，融合在 `fusion.py` | 读码 | `retrieval/fusion.py::fuse` |
| 父块去重后取 top-k | 见 `_dedupe_parent` 调用链 | 读码 | `…::_finalize` |
| 网关并发上限不提供 team 级 | `UpdateTeamRequest` 无该字段 | 推断 | 管理面 schema |

没有证据表的写作一定会滑向「听起来很合理」。等级定义见本文第五节。

---

## 一、入口普查：把所有触发方式列全

同一个模块往往不止一个入口。漏一个入口，就会漏掉一整条分支。

按形态逐个查：

- **HTTP**：路由注册文件里搜路径前缀；别只看 controller，注意网关/BFF 是否还有一层转发。
- **前端**：页面组件、按钮事件、API client 函数；同一个接口可能被多处调用。
- **消费者 / 队列**：topic 订阅、worker 注册。
- **定时任务**：cron、调度器配置。
- **CLI / 脚本**：运维脚本、迁移脚本、一次性修数脚本。
- **内部调用**：其他服务直接 import / RPC 的路径。
- **工具协议**：MCP 工具、函数调用注册表等。

**判据**：把入口清单写出来，逐条问「这条会不会走到我准备写的核心函数？」答不上就去 grep。

---

## 二、分层追踪：选一条真实请求走到底

不要按目录读代码，按**请求**读。选一条最有代表性的（主流程 + 一条失败路径），逐层记四件事：

| 层 | 入参 | 出参 | 副作用 | 失败行为 |
|---|---|---|---|---|
| 前端 | | | | |
| 网关 / 中间件 | | | | |
| 服务入口 | | | | |
| 领域逻辑 | | | | |
| 数据层 | | | | |
| 外部依赖 | | | | |

- **出参写形状，不写类型名**：`{items: [{id, score, source}], truncated: bool}` 比 `List[SearchHit]` 更能让读者理解契约。
- **副作用必须列**：写库、发消息、写缓存、记审计、扣配额。
- **失败行为单独一行**：报错？降级？回退到旧路径？静默跳过？这行往往是整个模块最承重的设计。

### 每一层都问五个问题

1. 输入是什么，谁给的？
2. 输出是什么，给谁用？
3. 这里做了什么转换 / 判定？
4. 失败时会发生什么，调用方知道吗？
5. 换一种做法会怎样，为什么没换？

## 三、配置三处核对（高频静默失效源）

同一个参数可能存在于三个地方，而且**值不一定相同**：

| 位置 | 例子 | 风险 |
|---|---|---|
| 代码默认值 | `config.py` 的类属性 / 模块常量 | 只是兜底，未必生效 |
| 环境变量 / 配置中心 | Nacos、Consul、`.env`、K8s ConfigMap | **优先级通常更高**，会压过代码默认值 |
| 迁移 / seed / 管理面 | SQL 迁移、初始化脚本、数据库里的租户配置 | 运行期真正读到的可能是它 |

核对方法：

1. 找到读取该键的唯一入口（`settings.xxx` / `getenv` / 配置客户端）。
2. 追出优先级：谁覆盖谁。
3. 分别查三处的实际值，写进证据表。
4. 如果只有代码默认值、没有配置项，明确写「是模块常量，不随环境变化」——这本身是设计决定。

**特别警惕**：改了代码默认值，但线上配置中心里还是旧值 ⇒ 本地和测试全绿、生产行为不变，且没有任何报错。文档里必须写清「这个值从哪来」。

## 四、第三方依赖边界

读者最常问的一个问题是：「这是你们写的，还是库干的？」

对每段核心能力确认：

- 用的是哪个库、哪个版本；
- 是**直接调用**、**包装**，还是**替换了默认实现**；
- 库的默认行为里，有哪些被本项目依赖或覆盖（超时、重试、缓存、序列化、并发模型）；
- 上游升级会不会改变语义。

写法示例：「限流器不是自研，是 LiteLLM 的 `_PROXY_MaxParallelRequestsHandler_v3`，基于固定窗口计数器；本仓只做配置与管理面。」——这一句就把责任边界说清了。

## 五、证据分级

| 等级 | 判据 | 写法 |
|---|---|---|
| **实测** | 跑过命令 / 请求，能给出关键输出 | 「实测：写入 → 读回逐字相同」 |
| **读码** | 代码路径可达，能指到符号 | 「见 `path::symbol`」 |
| **推断** | 由结构或约束推出，没有直接执行 | 「推断：该表没有第二个写入口 ⇒ …」 |
| **未核** | 没验，或验不了 | 原样保留 `未核` |

纪律：

- 实测读数与推断**分开写**，不要让推断借实测的语气。
- **不要写一次性的读数当永久事实**。写「结论 + 怎么算出来的」，而不是把某次运行的数字抄进正文；数字会变，方法不会。
- 「测试全绿」不等于「验到了」：断言可能恒真（例如日志根本没被捕获、断言只匹配到了注释）。要么自己跑一遍端到端，要么标「未核」。

## 六、七种常见假象

### 1. 文件名与行为不符

`payment.ts` 可能不处理支付。**以调用链为准，不以文件名为准。**

### 2. 注释与代码不符

先问：**注释描述的那一支可达吗？** 不可达的分支，注释说什么都不算数；可达但与注释矛盾，以代码为准，并在文档里写清实际行为。

### 3. 默认值被环境覆盖

见第三节。凡是「默认值」三个字，都要追问一句「线上真的用这个值吗」。

### 4. 降级分支把失败伪装成成功

例如：向量服务挂了退回关键词检索、远程读失败退回本地缓存、解析失败退回空列表。这些分支必须写进机制链条，并说明**调用方能否感知**。

### 5. 跨服务身份 / 上下文靠约定传递

用户身份、租户、trace id 常常通过请求头或隐式上下文传递。漏传不会报错，只会**静默降级或越权**。文档要写清：谁注入、经过哪几跳、缺了会怎样。

### 6. 行号会漂

行号只作粗略参考。锚点优先用符号名；非写行号不可时，声明抽取点（哪个提交 / 哪次抽取），并明说会漂。

### 7. 「没人调用」的假零

判「某函数没人调用」前，至少查三种形态：

- 裸名：`foo(`
- 别名 / 解构：`const { foo } = mod` / `import foo as bar`
- 命名空间调用：`mod.foo(` / `Service::foo`

再查测试、脚本、配置里的字符串引用。三种都为零，才敢写「无调用方」。

## 七、读数的记录纪律

- 文档里只写**结论 + 方法**：「融合候选数由 `fusion_candidate_top` 控制，默认 30」比「这次跑出来是 30」更耐久。
- 需要写具体数值时，同时写**它的来源**（默认值 / 配置项 / 迁移 seed）。
- 实验性读数（延迟、命中率、token 数）如果必须写，标明测量条件；否则放台账，不放技术文档。
