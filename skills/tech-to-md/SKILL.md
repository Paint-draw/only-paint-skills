# 技术底层实现文档写作器（tech-to-md）

## 这个 skill 交付什么

一份文档，只回答三个问题：

1. **系统现在怎么跑** —— 请求从哪进、经过哪些层、每层做什么、层间传的数据长什么样；
2. **为什么这么设计** —— 选了什么方法、否掉了什么、各自的代价；
3. **这块功能怎么实现** —— 落到「用什么方法实现」这一层，不落到逐行代码。

读者有两类：**没接触过本项目、来学这套实现的人**，以及**未来的作者自己**（回溯「当初为什么这么设计」）。

因此验收标准不是「写全了」，而是：**别人问起这个模块怎么做的，作者读完这份文档能完整讲出来；外人读完能不看代码就理解机制。**

## 先分清产出物

| 用户想要 | 用哪个 skill | 产物特征 |
|---|---|---|
| 记住 / 讲清**这个仓里**某模块怎么实现 | **本 skill** | 绑定本仓与本技术栈，带代码锚点，讲机制与取舍 |
| 抽一套能搬到别的系统的业务规格 | `business-logic-extractor` | 技术栈无关，不写框架调用，供重实现 |
| 给业务方评审的现状需求文档 | `business-logic-reqdoc` | 零实现标识，不写字段名 / 类名 / 接口路径 |
| 全项目业务模块白皮书 | `business-logic-init` | 按业务模块建档，面向业务理解 |
| 查实现与文档的缺口 / 漏洞 | `business-logic-hunt` | 审计报告，只查不改 |

如果用户要的是「可移植」「给产品看」「不绑定技术栈」，本 skill 不适用——先说明边界，再换 skill。

## 六条原则

### 1. 照代码取证，不照文件名、注释和记忆

函数名可能撒谎，注释可能过期，记忆一定不完整。凡是写进文档的机制，都要能指到一段**可达的代码路径**或一次**实测输出**。读不到、验不了的，明写「未核」，不要用流畅的句子把它糊过去。

代码主要由 AI 生成时尤其要注意：**注释和命名描述的是它「打算做什么」，文档要写的是它「实际做了什么」**。两者不一致时，以可达代码为准，并在文档里写清实际行为——否则你记住的会是注释，而不是系统。

### 2. 停在「用什么方法」这一层

| ✅ 该写 | ❌ 不该写 |
|---|---|
| 用**固定窗口计数器**限流，窗口长度 60s，读窗口 → 判超限 → 计数由一段 **Lua 脚本原子完成** | 第 42 行 `counter += 1` |
| 两路召回**各出一份列表**，在全局做**加权 RRF**，`k = 60` | 调用 `rrf_fuse(a, b, weights)` |
| 关键词路**不降级**，因为评估链路要求「检索失败就是失败」 | 关键词路比较稳定 |
| 层间传的是 `{kb_ids, user_id, queries[]}`，子问题数 N 决定列表数 2(N+1) | 传了一个 `params` 对象 |

判据：**换一种语言重写，这段描述还成立吗？** 成立就是方法层；只有读这一份代码才成立，就是实现细节。

变量名、字段名、表名只在它们是**契约**时出现（请求参数、落库字段、事件名、配置键）——因为它们是别人对接时要用的东西。纯局部变量不进文档。

### 3. 每条断言标证据强度

四档，写在句子里或括注：

- **实测**：跑过，写清命令与关键输出；
- **读码**：代码路径可达，写明锚点；
- **推断**：由结构推出来的，写明推断依据（如「该分支没有第二个写入口，故…」）；
- **未核**：没验，保留 `未核` 二字。

实测读数与推断**分开写**。不要用「已验证」「应该没问题」这种模糊说法。

### 4. 先机制链条，后设计取舍

先让读者能在脑子里跑通一遍请求，再解释为什么这么设计。顺序反了，取舍就成了没有对象的空谈。

链条必须包含**层间数据形状**与**失败行为**——失败路径往往是这个模块最承重的部分（降级、回退、静默丢弃、错误即结果）。

### 5. 读者没有本仓历史

文档里出现的每一句，都必须是「不懂本仓编年史的人读了也能懂」的。内部术语首次出现就地给一句话定义；不要假设读者知道上一个版本长什么样、某个事故是什么。

反过来，**本仓历史、批次、提交、验收记录不进技术文档**——它们属于台账与 `git log`。技术文档重复一遍，只会两边都可能过期。

### 6. 只标 `★★` 承重点，不撒星

`★★` 只给「改错就会静默失效、且没人会发现」的地方（身份漏传、配置覆盖默认值、幂等被破坏、双向校验只做了一边）。普通重点用加粗即可。通篇是星等于没有星。

## 工作流

### 第 0 步：定范围与模式

开工前用 3–5 行确认，不要一问一答拖成访谈：

- **模块名**：决定默认落点 `docs/<模块>实现.md`；
- **代码根**：哪个目录 / 哪几个服务；
- **入口**：前端页面？HTTP 路由？定时任务？CLI？MCP 工具？
- **读者**：只给自己，还是也要给外部人看（影响理论补课的深度）；
- **模式**：目标文档是否已存在。

**先搜同主题文档，再决定新建还是增量**：在目标仓 `docs/` 与全仓搜一遍模块关键词，确认没有**另一份**已经讲同一主题的文档。只看精确目标路径会造出第二份会漂移的地图——两份各自过期时，读者不知道该信哪份。若同主题文档已存在但路径不同：优先增量更新它；确需新建时，在文首写清与旧文的边界，并与用户确认。

**没有可确认的用户时**（例如被派发执行、任务已给定模块 / 代码根 / 入口 / 读者）：不要停下等确认，直接进入第 1 步，并在文首写明本次覆盖的范围与不覆盖的部分。

目标文档已存在 ⇒ 走**增量模式**（见文末），先读旧文再动笔。

### 第 1 步：取证

按 `references/取证指南.md` 读代码，先产出一张**证据表**（断言 / 证据 / 等级 / 锚点），再开始写正文。没有证据表的写作一定会滑向「听起来很合理」。

证据表是**过程草稿**，不必整张搬进文档；但两样东西要留下：关键结论的**实测命令与条件**，以及**未核项清单**——写进文末可选附录「取证方式与未核项」。

必做的五件事：

1. **入口普查**：把所有能触发这个模块的入口列全（路由、消费者、定时任务、前端 API client、CLI、内部调用）。
2. **分层追踪**：选一条真实请求，从入口跟到落库 / 出站 / 返回，每层记「入参 / 出参 / 副作用 / 失败行为」。
3. **配置三处核对**：代码默认值、配置中心或环境变量、迁移与 seed——三者可能各不相同。特别留意「配置中心压过代码默认值」这类静默覆盖。
4. **依赖边界**：这段到底是「调库」还是「自己实现」，库的版本是多少，覆盖或依赖了哪些默认行为。
5. **调用点普查**：要写进文档的公共符号 / 全局状态 / 隐式上下文（如 `ThreadLocal`、请求级单例），用 grep 找出**全部**调用点与测试，确认没有漏掉的入口或旁路。

### 第 2 步：机制建模

动笔前先在草稿上建三样东西：

1. **一页概览链路**：`入口 → ①… → ②… → 输出`，每个环节旁注「怎么处理」与「失败怎么办」。这张图必须能从入口独立走到出口，不能中间断一节。
2. **承重点清单**：哪些地方一旦改错就静默失效？为什么？
3. **取舍清单**：每个关键选择，写下「选了什么 / 否了什么 / 各自代价」。没有 B 方案的「为什么」通常说明还没挖到。

### 第 3 步：成文

复制 `assets/技术实现文档.template.md`，按 `references/体例.md` 写。

几条会直接决定成品质量的规则：

- **章节按请求链路排，不按代码目录排**。跨层的横切主题（身份、配置、错误处理、计量）单独成节。
- **读者需要前置知识时，先补一段「理论」再讲实现**（例如讲限流先讲四种经典计数法，讲缓存先讲精确匹配与语义匹配的差别）。理论段只写到「能读懂本实现」为止。
- **每个主题写全五要素**：有什么方法 / 实现什么 / 解决什么问题 / 优缺点 / 原来怎么做的、哪里不好。某一项确实没有，写「无」，不留空白。
- **参数写三件事**：实际值、默认值、覆盖来源（代码常量 / 环境变量 / 配置中心 / 租户配置）。只写「可配置」等于没写。
- **代码锚点用符号名**：`path/to/file.py::symbol`。非给行号不可时，同一处声明抽取点（哪个提交 / 哪次抽取），并说明行号会漂。
- **表格优先于长段落**：对比、参数、失败分支、护栏层次，几乎都能表格化。

### 第 4 步：自检

先跑机械检查（脚本在**本 skill 目录**下，不在目标仓里，路径要写全）：

```bash
python "<本 skill 目录>/scripts/check-doc.py" "<目标仓>/docs/<模块>实现.md"
```

再逐项过 `references/自查清单.md`。机械检查只查结构、禁写项与可疑措辞；内容是否讲透，靠清单和下一步。

### 第 5 步：口述验收与速答卡

这是本 skill 与普通「写文档」最大的差别：**文档要能支撑口述**。

- 只用「〇、一页概览」讲 60 秒，看能不能讲完整条链路；
- 任挑一节，看能不能讲 3 分钟（方法 → 为什么 → 代价 → 失败怎么办）；
- 列出最可能被追问的 5 个问题，逐个确认正文答得出。

然后把它们压成文末的**速答卡**（可选附录）。速答卡只能压缩正文已有的事实，**不许引入正文没写过的新断言**——否则它会变成第二份会过期的文档。

## 增量模式（目标文档已存在）

1. 先读旧文，建一张「旧编号 → 主题」表。
2. **`§N` / `§N.M` 不重排、不合并**。正文可以整段重写，编号是接口——仓内代码注释、迁移文件、台账都可能按它指路。新增内容用 `§N.M`；确需新增顶层节时先问用户。
3. **「行为变更」只追加**，每行写「变更 + 看哪节」，不写日期与批次。
4. **「已知的粗糙处」可以销账**：问题消失就删掉该行，并在「行为变更」记一条；不要写「原文如此，已订正为…」这类订正沿革。
5. 旧文里的事实要**重新取证**，不要因为「上一版这么写」就保留。代码可能已经变了。

## 交付

- 默认写到 `docs/<模块>实现.md`（与仓内既有 `<模块>实现.md` 命名一致）。用户指定别处则从其指定。
- 写完向用户报告：文档路径、覆盖的链路范围、**明确的未核项**、以及自检结果。不要只回一句「写好了」。
- 文档不是一次性产物：代码大改后回来走增量模式，比重新写一遍便宜得多。
