# 模式③ 执行计划 · 方法（深版）

> SKILL.md 给了"执行 → 验证 → 审查 → 确认白皮书同步"的骨架；每一环的边界、失败怎么办、几环之间怎么传数据、冲突听谁的，在这里。

## 一、执行边界 —— 分步执行，带检查点，不是一口气冲到底

用 `superpowers:executing-plans` 打开计划文档，**按步骤逐步实现**：

- **一步一验，不攒到最后**：完成计划里的一个步骤 → 就地做该步的验证（见第二节选层级）→ 过了再进下一步。攒到最后一起验，出问题定位成本翻倍。
- **检查点在哪**：计划里标了「复杂度/风险=高」的步骤、以及涉及数据迁移/删除/外部回调的步骤，做完**先停下向用户汇报**再继续（人工介入点），不自动往下推。低风险步骤连续做无妨。
- **工作区隔离按规模自判**：小改直接在当前区改（`git stash`/`git checkout` 回滚即可）；中改看 git 状态是否干净再定；大改（10+ 文件/跨模块/数据库迁移/破坏性变更）才用 `superpowers:using-git-worktrees` 隔离。worktree 是安全网不是手铐，大部分日常执行不需要它。卡壳走 `superpowers:systematic-debugging`。

## 二、验证分层 —— 按改动面选层级，说清做到了哪层

"做代码验证"不是一个动作，是一把梯子。用 `superpowers:verification-before-completion`，**按本次改动面选要爬到哪一层**，并在收尾如实说明做到了哪层：

| 层级 | 做什么 | 什么时候必须做 |
|------|--------|----------------|
| L0 编译/构建 | build 通过 | 永远——但**build 通过 ≠ 功能完成**，只是起点 |
| L1 单元测试 | 跑相关单测 | 改了后端规则/纯函数/算法 |
| L2 集成测试 | 跑集成/EF 测试 | 改了数据访问、跨服务、事务 |
| L3 接口冒烟 | 用 Swagger/curl 真实调改动的接口，看真实响应 | 改了任何接口（路径/参数/权限/返回） |
| L4 端到端 | 各端点进真实页面走一遍 | 改了用户可见流程；多端都要各走一遍 |

选层判据：**UI 文案/样式类** → L0+L4；**后端规则/接口类** → L0+L1(有则)+L3，动了数据/事务加 L2；**贯穿全链路的需求** → L0→L4 全爬。计划文档「验证与验收」里标的层级就照它做。

## 三、执行 → 验证 → 审查：几环之间怎么传数据

三环不是各干各的，有明确的数据流：

1. **执行**产出：改了哪些文件、对应计划的哪些步骤（做一张"步骤→改动"对照，交给验证和审查）。
2. **验证**产出：每层级跑了什么命令、真实输出、哪些验收项过了/没过。**这份结果要带给审查**——审查员据此知道"哪些已被验证、哪些还没"。
3. **审查**产出：按下面第四节分级的意见。**阻塞项回写进计划文档「未决/受阻」并回到执行**；建议项记入模块文档「未决问题」留待后续。审查意见不落文档 = 丢失。

## 四、代码审查 —— 带着业务背景审，意见分级

用 `superpowers:requesting-code-review`，但**必须给审查员业务上下文**，否则它只能看代码规范、判断不了业务对错。交给审查的材料要含：

- **本次业务背景**：完善文档路径 + 一句话"这次要把 X 改成 Y"。
- **预期行为**：正向/失败/边界分别该怎样（引完善文档目标）。
- **重点关注维度**：业务规则是否正确落地、状态流转有没有缺分支、受影响功能（`[[id]]` 那些）有没有真的同步改、有没有违反 `docs/rules/` 的项目强约束。

**审查意见分两级**：
- **阻塞级**：业务实现错、规则违反、受影响功能漏改 → 必须回执行修。
- **建议级**：可读性、非阻塞优化 → 记未决问题，不拦收尾。

收到审查用 `superpowers:receiving-code-review` 理性对待——**不盲从也不盲拒**，技术上存疑的先核实再改。

## 五、失败与冲突：if-fail 分支和裁决

不给失败分支，流程一遇挫就卡死。约定：

- **执行某步失败** → `systematic-debugging` 定位 → 修 → 重跑该步验证。同一步**连续卡住**（如两三轮仍不过）→ 停，把现象写进计划文档「受阻」，**回报用户**（人工介入），不硬冲、不跳过。
- **验证不过** → 回执行修，**不得带病进入审查或收尾**。验证是硬门槛。
- **审查判"需重大修改"** → 阻塞项回执行；范围过大 → 可能是计划本身有问题，回模式②修计划文档再执行。
- **验证与审查结论冲突怎么裁决**：两者是**不同维度**，不是二选一——
  - 验证过（能跑）但审查判**阻塞**（业务错/违规）→ **以审查为准**，回去修。能跑不等于对。
  - 验证不过但审查说"问题不大" → **以验证为准**，先修到能跑对。跑不对没有"问题不大"。
  - 只有当审查是**建议级**、且验证已过 → 才可收尾，建议记未决。
  - 一句话：**任一维度的"阻塞/不过"都拦收尾；只有两边都到绿灯（验证过 + 审查无阻塞项）才算完成。**

## 六、多模块并行修改

计划涉及多个业务模块同时改时：

- **验证**：能按模块独立验的**分模块验**（各自 L1/L3），最后再跑一次**跨模块的 L4 端到端**看联动。
- **审查**：按模块分别审（每块带自己的业务背景），再整体审一次接缝处（模块间调用、共享表）。
- **收尾同步**：**每个被改模块**各自回写自己的 `docs/business-logic/<模块>.md`，一个都不能漏——拿完善文档里 `[[id]]` 清单逐个核。

## 七、收尾：确认白皮书已同步（顺序明确，收尾必做）

**顺序**：执行 → 验证过 → 审查无阻塞 → **然后才做文档同步**（放在最后，因为要等代码定稿，避免边改边回写、白写）。这一步不是"注意事项"，是收尾的正式一环。

> 常见疑问：收尾时"发现文档还没改"，要不要重新触发审查？——不用。文档同步本来就安排在审查**之后**，此刻文档未更新是**预期状态**，现在补写即可；且这一步改的只是文档、不是代码，**不需要**重新跑代码审查。唯一例外：回写文档时发现代码实际行为和已确认的目标逻辑对不上——那不是文档问题，是代码问题，回第五节失败分支处理。

**文档同步的验收标准**（不是"文件被 edit 过就算数"）：逐条核对**改动内容与代码变更是否吻合**——
- [ ] 对应 `docs/business-logic/<模块>.md`：用户操作/展示、接口清单（新增/改的接口都登记）、数据表、状态流转、影响功能，是否都按本次变更更新了？
- [ ] 完善文档 `[[id]]` 清单里每个受影响模块的文档，都同步了吗？
- [ ] 根目录《业务逻辑白皮书》里该模块的**状态**（改动大可先回到 `草稿`，核对后升 `已核对`）和**最近更新日期**，更新了吗？
- [ ] （轻量溯源）模块文档 frontmatter 记一句**关联计划文档路径 + 本次提交**，让文档能反查到是哪次改动、哪个 commit 带来的。

没同步就补上。**不同步 = 白皮书和代码脱节，本模式最容易漏的坑。**

## 八、交接验收 —— 模式③的最后一步（和①②的「交接」对称）

白皮书同步核对完，不是默默结束。①收尾有「交接」、②收尾有「交接」，③同样要把结果**正式交给用户验收**（人工介入点）——否则整条流水线最后一环没人拍板，"完成"只是 AI 单方面宣布。验收汇报要含：

- **做了什么**：对应计划的哪些步骤、改了哪些端/文件（引第三节那张"步骤→改动"对照）。
- **验证到哪层**：各层级跑了什么、真实结果如何（引第二节，如实说做到了哪层、没做哪层）。
- **审查结论**：阻塞项已清零；建议级记入了哪些未决问题。
- **文档同步**：回写了哪些模块文档（含 `[[id]]` 清单）、根白皮书状态更新情况。

用户验收通过才算真正完成。用户提出问题 → 按第五节失败分支处理：实现层面的小问题回执行修，需求/方向层面的问题回模式②改完善文档与计划，不在验收环节口头打补丁。
