# 后端代码业务逻辑分析指引

后端是业务逻辑的核心承载层。绝大多数硬性业务规则——数据约束、事务边界、权限校验、状态转换、外部集成——都在后端。后端分析的质量直接决定规格文档的可用性。

## 分析目标

从后端代码中提取：
1. **数据如何存储与约束**（模型、schema、迁移）
2. **接口如何定义与校验**（路由、controller、DTO、validator）
3. **业务规则如何执行**（service、domain logic）
4. **状态如何流转**（状态机、事件）
5. **外部如何集成**（第三方调用、webhook、消息）
6. **安全如何保障**（认证、授权、审计、限流）
7. **异常如何处理**（错误码、重试、补偿）

## 按层分析

### 1. 路由层（Routes / Controllers）

入口层，定义所有对外接口。

**要提取的信息**：
- 所有相关端点（HTTP 方法 + 路径）
- 每个端点的认证要求（公开、需登录、需特定角色）
- 请求参数（来源：body、query、path、header）
- 响应格式（成功、各种错误）
- 中间件链（鉴权、限流、日志、CORS）
- 接口级别的配置（超时、缓存策略）

**分析技巧**：
- 从路由配置文件入手（`routes.ts`、`controllers/`、`@Controller` 注解）
- 查看每个端点绑定的中间件，中间件往往承载横切逻辑
- 注意路由前缀和版本号，体现 API 演进
- 查看路由守卫/拦截器，找权限和限流逻辑

### 2. 请求校验层（DTO / Validator）

入口校验，拦截非法请求。

**要提取的信息**：
- 每个字段的校验规则（类型、必填、长度、范围、格式、枚举）
- 跨字段校验（如"开始时间 < 结束时间"）
- 自定义校验注解/装饰器
- 校验失败的错误格式

**分析技巧**：
- 查找 DTO/Request 类定义，看校验注解（`@NotNull`、`@Size`、`@Pattern`、class-validator、Pydantic validators）
- 查找自定义校验函数
- 注意校验顺序——有些校验依赖其他校验通过

**重要**：入口校验只是第一道防线，业务校验在 service 层。两层都要记录。

### 3. 服务层（Service / Domain Logic）

业务核心。这是分析的重点，通常也是最复杂的部分。

**要提取的信息**：
- 每个业务操作的完整流程（步骤、顺序、依赖）
- 业务规则（计算公式、判断条件、阈值）
- 状态转换逻辑（什么条件下从状态 A 到状态 B）
- 事务边界（哪些操作在同一事务内）
- 并发控制（锁、乐观锁、CAS）
- 调用了哪些其他 service（依赖关系）
- 调用了哪些外部服务
- 发布了哪些事件
- 异常处理（抛什么异常、如何恢复）

**分析技巧**：
- 从 controller 调用的 service 方法入手，逐行阅读
- 画出方法调用图（谁调谁）
- 标注每个数据库操作，理解事务范围
- 标注每个外部调用，理解失败影响
- 注意 `@Transactional`、`with transaction`、`unitOfWork` 等事务标记
- 注意 `synchronized`、`Lock`、`SELECT FOR UPDATE` 等并发控制
- 注意 `publishEvent`、`emit`、`send` 等事件发布

**关键**：service 层的逻辑要追踪到底——调用的其他 service 也要打开看，不能只看方法名猜行为。

### 4. 数据模型层（Model / Entity / Repository）

数据结构和持久化逻辑。

**要提取的信息**：
- 所有相关实体及其字段（类型、约束、默认值）
- 实体关系（一对多、多对多、外键、级联）
- 索引（唯一索引、普通索引——它们暗示查询模式和业务约束）
- 数据库约束（check、unique、not null、foreign key）
- 软删除机制
- 审计字段（created_at、updated_at、version）
- 仓储层的特殊查询逻辑

**分析技巧**：
- 查看 ORM 实体定义（`@Entity`、`db.Model`、Schema）
- 查看迁移文件（migration）——约束和索引往往在这里定义
- 查看 schema 文件（Prisma、TypeORM、SQLAlchemy 的 schema）
- 查看仓储层（Repository）的自定义查询方法
- 注意乐观锁字段（`@Version`、`version` 字段）

**重要**：数据库约束是业务规则的最后防线，必须记录。一个 `UNIQUE(user_id, status)` 约束意味着"同一用户同时只能有一个该状态的记录"——这是业务规则。

### 5. 中间件与拦截器（Middleware / Interceptors）

横切逻辑，常被忽略但承载重要业务规则。

**要提取的信息**：
- 认证中间件（如何解析 token、如何验证、如何注入用户信息）
- 授权中间件（角色检查、权限检查、数据范围检查）
- 限流中间件（限流策略、限流维度、超限响应）
- 日志中间件（记录什么、格式、脱敏）
- 审计中间件（哪些操作审计、记录什么）
- 幂等中间件（如何识别重复请求、如何返回缓存结果）
- 请求追踪（traceId 生成与传递）

**分析技巧**：
- 查看全局中间件配置
- 查看路由级中间件绑定
- 查看拦截器/过滤器（响应处理、异常处理）

### 6. 外部集成层（External Service / Client）

与第三方和内部其他服务的交互。

**要提取的信息**：
- 调用了哪些外部服务（服务名、接口、用途）
- 调用契约（请求格式、响应格式、错误码）
- 超时与重试策略
- 熔断与降级策略
- 鉴权方式（API Key、证书、OAuth）
- 回调/Webhook 处理（接收哪些、如何验签、如何处理）
- 幂等性保证（外部调用失败重试时如何防重复）

**分析技巧**：
- 查找 SDK / Client 类的定义和使用
- 查找 webhook 回调路由
- 注意重试逻辑（`retry`、`@Retryable`、`tenacity`）
- 注意熔断器（`@CircuitBreaker`、`Hystrix`、`resilience4j`）

### 7. 异步任务与消息（Background Jobs / Messages）

异步业务逻辑，常被遗漏。

**要提取的信息**：
- 定时任务（执行频率、处理逻辑、锁机制防重复执行）
- 队列消费者（消费哪些队列/主题、处理逻辑、失败重试）
- 事件发布（发布哪些事件、事件结构、可靠投递机制）
- 延迟任务（如"30 分钟未支付自动关闭"）

**分析技巧**：
- 查找 cron 表达式或定时任务注解（`@Scheduled`、`@Cron`、`celery beat`）
- 查找队列消费者（`@RabbitListener`、`@KafkaListener`、`@Consumer`、celery task）
- 查找事件发布（`publishEvent`、`emit`、`producer.send`）
- 查找延迟队列/定时任务（Redis ZSet、RocketMQ 延迟消息、定时任务扫表）

### 8. 配置层（Config）

可配置的业务参数。

**要提取的信息**：
- 业务相关的配置项（阈值、开关、超时时间）
- 配置默认值
- 配置来源（环境变量、配置中心、数据库）
- Feature flag 及其影响的行为分支

**分析技巧**：
- 查找配置类/文件（`config.ts`、`application.yml`、`settings.py`）
- 查找环境变量读取（`process.env`、`os.environ`、`@Value`）
- 查找 feature flag（`if featureEnabled('xxx')`）

### 9. 测试代码（Tests）

测试是业务规则的"可执行文档"。

**要提取的信息**：
- 测试用例揭示的边界条件
- 测试用例揭示的预期行为
- 测试中的 mock 揭示的外部依赖
- 测试数据揭示的典型场景
- 未被测试覆盖的场景（潜在风险）

**分析技巧**：
- 阅读单元测试（service 层逻辑测试）
- 阅读集成测试（完整流程测试）
- 阅读测试工具函数（`createTestOrder`、`mockPaymentSuccess`）——它们揭示典型数据
- 注意测试名称中的"when...should..."——那是业务规则的自然语言描述

### 10. 数据库迁移（Migrations）

迁移文件是业务规则演进的历史记录。

**要提取的信息**：
- 表结构变更历史
- 约束变更（新增的 unique、check 约束往往是补丁——说明之前出过问题）
- 数据迁移逻辑（如"把所有 status=0 的记录改为 status=PENDING"）
- 索引变更（新增索引暗示了性能问题或新的查询模式）

**分析技巧**：
- 按时间顺序阅读迁移文件
- 注意迁移中的注释——往往解释为什么做这个变更
- 注意数据迁移——它们揭示历史数据状态

## 后端特有业务逻辑清单

以下是后端特有、容易遗漏的业务逻辑：

### 事务与一致性
- [ ] 事务边界（哪些操作原子完成）
- [ ] 隔离级别（如使用了非默认隔离级别）
- [ ] 乐观锁/悲观锁
- [ ] 分布式事务（Saga、TCC、本地消息表）
- [ ] 最终一致性保证（对账、补偿）

### 并发控制
- [ ] 资源锁（数据库行锁、分布式锁）
- [ ] 防重复提交（幂等键、唯一约束）
- [ ] 防超卖（库存扣减的并发控制）
- [ ] 限流（接口级、用户级、IP 级）

### 幂等性
- [ ] 哪些接口需要幂等
- [ ] 幂等键的生成与传递
- [ ] 幂等结果的缓存与返回
- [ ] 幂等过期时间

### 安全
- [ ] 认证机制（JWT、Session、API Key）
- [ ] 授权策略（RBAC、ABAC、ACL）
- [ ] 数据权限（行级、字段级）
- [ ] 敏感数据加密（存储、传输）
- [ ] SQL 注入防护
- [ ] XSS / CSRF 防护
- [ ] 签名验证（外部回调）
- [ ] 审计日志

### 可靠性
- [ ] 重试策略（哪些操作重试、退避算法）
- [ ] 熔断与降级
- [ ] 死信队列处理
- [ ] 补偿机制
- [ ] 对账机制

### 性能
- [ ] 缓存策略（缓存什么、失效策略）
- [ ] 批量操作优化
- [ ] 异步化处理
- [ ] 分库分表（如有）
- [ ] 读写分离（如有）

## 常见陷阱

1. **只看 controller 不看 service**：controller 往往只是转发，真正的逻辑在 service。一定要追到 service 层。

2. **只看 service 不看 model/migration**：数据约束是业务规则的一部分。一个 `UNIQUE` 约束、一个 `CHECK` 约束都是业务规则。

3. **忽略异常处理**：`catch` 块里的逻辑往往揭示边界情况和恢复策略，是业务规格的重要部分。

4. **忽略事务注解**：`@Transactional` 的范围（哪些方法在事务内、传播行为、隔离级别）直接影响业务正确性。

5. **忽略异步逻辑**：定时任务、消息消费者、事件处理器都是业务逻辑，且最容易遗漏。

6. **把框架特性当成业务逻辑**：`@RestController`、`@Autowired` 是框架细节。业务逻辑是"这个接口需要登录且只能查自己的数据"。

7. **忽略配置项**：硬编码的阈值是业务规则，配置化的阈值更是业务规则。`if amount > MAX_AMOUNT` 中的 `MAX_AMOUNT` 要记录。

8. **忽略注释和 TODO**：注释往往解释"为什么这样实现"——这是业务规则存在的原因，对重实现至关重要。

9. **只看成功路径**：错误处理、边界情况、补偿逻辑才是业务逻辑的难点，必须重点分析。

10. **忽略测试**：测试用例是业务规则的精确描述，比代码注释更可靠。

## 输出建议

后端分析结果在规格文档中主要落入以下章节：
- **第 4 章 数据模型**：实体、字段、约束、索引
- **第 5 章 API 契约**：端点、请求响应、错误码
- **第 6 章 业务规则**：校验、计算、状态转换、权限
- **第 8 章 集成点**：外部服务、内部依赖、事件
- **第 9 章 安全与合规**：认证、授权、审计、限流
- **第 10 章 边界情况与错误处理**：并发、失败恢复
- **第 11 章 实现备注**：事务、并发、性能
