# 业务逻辑抽取器（Business Logic Extractor）

## 目的

从现有代码库中抽取业务逻辑，生成一份**可移植的业务规格文档**——描述功能"做什么"和"如何表现"，而不绑定任何特定框架、语言或技术栈。这份文档应当让另一个 AI（或开发者）在完全无法访问原始代码库的情况下，仅凭此文档就能在新系统中重新实现相同功能。

输出的不是代码评审，也不是现有代码的文档注释，而是一份**业务行为规格书**。

## 核心原则

### 1. 前端 + 后端，缺一不可

一个功能只有从"用户点击"追踪到"数据库写入"再返回到"界面更新"，才算被完整理解。跳过任何一侧都会产出残缺的规格，导致重实现时出现 bug。

- 只看后端 → 遗漏客户端校验规则、UI 状态机、加载/错误态处理、防重复提交、本地缓存策略
- 只看前端 → 遗漏服务端约束、事务边界、并发控制、权限校验、外部服务集成、异步任务

即使用户说"逻辑都在后端"，前端依然包含交互规则、表单校验、状态管理这些业务逻辑的一部分。主动分析另一侧，不要等用户提醒。

### 2. 技术栈无关的输出

规格描述行为和规则，而非框架调用。

- 写"校验手机号格式为 11 位数字"，不写"用 Joi.string().regex(/^1\d{10}$/)"
- 写"创建订单时在数据库层面保证订单号唯一"，不写"加 UNIQUE INDEX"
- 写"支付成功后发送异步消息通知库存系统"，不写"用 RabbitMQ publish 到 exchange X"

但实现层面的关键决策（如"必须保证幂等性"、"需要分布式锁"）要保留，因为这些是业务规则的一部分，只是用技术栈无关的语言描述。

### 3. 完整性优先于简洁性

每一条业务规则、校验、边界情况、状态转换都必须被捕获。遗漏一条规则 = 重实现时多一个 bug。宁可文档冗长，不可遗漏。

### 4. 追踪而非假设

读真实代码。不要从函数名或文件名推断行为——打开文件，跟随逻辑走一遍。`processPayment` 函数可能根本不处理支付，真正的支付逻辑可能在 `orderService.completeOrder` 里。

### 5. 隐性规则同样重要

业务逻辑藏在这些地方，都要扫到：
- 测试用例（揭示边界条件和预期行为）
- 数据库迁移与 schema 约束（unique、check、foreign key 都是业务规则）
- 配置文件（环境变量、feature flag、限流阈值）
- 错误消息与 i18n 文案（揭示错误场景）
- 注释与 TODO（解释规则存在的原因）
- 中间件与拦截器（权限、日志、限流往往在这里）
- 定时任务与队列消费者（异步业务逻辑）

## 工作流程

### 第一步：明确范围

读任何代码之前，先和用户确认：
- 要抽取哪个功能/模块（如"微信支付"、"优惠券核销"）
- 代码库在哪里（目录路径或仓库地址）
- 是否有特定场景需要聚焦（如"只看退款流程"）
- 有哪些已知的相关功能需要纳入或排除

如果用户请求模糊，主动追问。"抽取支付逻辑"——是否包含退款、查询、回调？是否包含优惠券抵扣的联动逻辑？范围不清就开始读代码，容易遗漏或越界。

### 第二步：定位所有相关代码

单个功能的业务逻辑通常散落在：

**后端**：controller、service、model/entity、route、middleware、validator、migration、test、config、DTO/schema 定义

**前端**：page/view、component、API client 函数、state store（Redux/Vuex/Pinia 等）、form validator、route guard、type/interface 定义

**共享**：API schema（OpenAPI/GraphQL schema）、错误码常量、i18n 文案、枚举定义

**基础设施**：cron job、queue worker、webhook handler、event listener、scheduled task

使用 `scripts/code-scanner.py` 按关键词扫描候选文件，然后逐个人工验证文件是否真的相关。

**关键提醒**：不要只靠文件名匹配。`payment.ts` 可能无关，而真正的支付逻辑可能藏在 `order-service.ts` 里。文件名和内容搜索都要用。

### 第三步：深度分析

逐个阅读定位到的文件。对每个文件提取：
- 它实现了什么业务规则或行为
- 它如何与系统其他部分连接
- 它处理了哪些边界情况
- 它可能产生哪些错误

前端分析指引见 `references/frontend-analysis.md`，后端分析指引见 `references/backend-analysis.md`。

**追踪完整的用户旅程**：选一个用户动作（如"用户点击支付"），跟随它穿过每一层——前端事件处理 → API 调用 → 后端路由 → controller → service → model → 数据库 → 响应 → 前端状态更新 → UI 重渲染。记录每一步。

### 第四步：综合成规格文档

将所有发现整合成一份结构化文档，使用 `references/output-template.md` 中的模板。

规格必须自包含——一个无法访问原始代码库的开发者（或 AI）应当能仅凭此文档重新实现该功能。

### 第五步：完整性检查

定稿前，逐项过一遍 `references/extraction-checklist.md`。这份清单确保不遗漏。

常见容易遗漏的点：
- 数据库约束与索引（它们也编码了业务规则）
- 限流与熔断
- 幂等性要求
- 审计日志
- 每一层的权限校验（前端、API 网关、service、数据查询）
- 客户端校验（往往与服务端校验不完全一致）
- UI 的加载态、错误态、空态、禁用态
- Webhook/回调处理（包括重复回调、延迟回调、失败重试）
- 并发与竞态条件
- 时区与货币精度处理
- 软删除与数据归档策略

### 第六步：输出

将最终规格保存为 Markdown 文件到 `/home/z/my-project/download/[功能名]-business-logic.md`。

如果功能较大，考虑拆分为多个文件（如 `payment-core.md`、`payment-refund.md`、`payment-webhook.md`）加一个索引文件。

## 输出格式概览

规格文档包含以下顶层章节（完整模板见 `references/output-template.md`）：

1. **功能概述** — 目的、范围、参与者
2. **术语表** — 规格中使用的领域术语
3. **用户流程** — 主流程、备选流程、异常流程（含文字版时序图）
4. **数据模型** — 实体、字段、关系、约束
5. **API 契约** — 端点、请求/响应结构、错误码
6. **业务规则** — 校验规则、计算规则、状态转换、权限规则
7. **前端行为** — UI 状态、交互、客户端校验、错误展示
8. **集成点** — 外部服务、内部依赖、事件
9. **安全与合规** — 认证、授权、数据保护、审计
10. **边界情况与错误处理** — 边界条件、失败场景、恢复流程
11. **实现备注** — 算法、性能、并发、事务
12. **重实现指引** — MVP 范围、推荐阶段、测试策略

## 重要提醒

- **永远不要跳过前端**。即使用户说"后端有全部逻辑"，前端依然包含校验、状态管理、UX 规则这些业务逻辑的一部分。
- **永远不要跳过后端**。前端无法揭示服务端约束、事务、集成。
- **仔细读测试**。测试往往揭示实现代码中不明显的边界条件和预期行为。
- **检查迁移和 schema 文件**。数据库约束（unique、check、foreign key）是在数据层强制执行的业务规则。
- **留意注释和 TODO**。它们有时解释规则存在的原因，这对正确重实现至关重要——知道"为什么"才能判断"能否改"。
- **捕获"为什么"，不只是"是什么"**。如果某条规则因合规或业务原因存在，记录这个原因。它影响重实现时该规则能否调整。
- **区分硬约束与软约束**。"金额必须大于 0"是硬约束；"建议用户名至少 4 位"是软约束。规格中要标明。
- **记录不确定性**。如果某段代码的行为无法确定（如依赖运行时配置），明确标注"此处行为依赖 X 配置，需向用户确认"。
