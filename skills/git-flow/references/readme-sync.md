# README 同步（提交/推送前按需更新）

**核心原则**：README.md 是项目的对外门面，必须始终描述**当前最新实现**。任何 `git commit` / `git push` 前，先检查本次改动是否让 README 描述与实际实现不一致；不一致就先更新 README 再提交，保持一致才直接提交。

## 何时需要更新（触发条件）

改动改变了项目对外可见的实现，提交前**必须**同步 README：

| 改动类型 | README 需要更新 |
|---|---|
| 新增功能 / 模块 | 在功能特性/目录章节增加描述 |
| 修改现有功能行为 | 更新对应功能的描述 |
| 删除功能 | 从功能特性列表移除，不留「已废弃」占位 |
| 接口 / API / 命令 / 路由变化 | 更新使用说明、参数、示例 |
| 配置 / 环境 / 部署方式变化 | 更新配置 / 部署章节 |
| 技术栈 / 架构变化 | 更新架构 / 技术栈章节 |

以下改动**不触发** README 更新：

- 修 bug（修复后的行为与 README 描述一致，只是实现修正）
- typo、注释、代码格式
- 重构（对外行为不变）
- 依赖小升级（README 未承诺具体版本）

## 判断流程（每次 commit 前）

1. `git status --short` + `git diff --stat` 看改了哪些文件。
2. 读 README.md 中与改动相关的章节。
3. 判断：改完代码后，README 描述是否与实际实现不一致？
   - **不一致** → 先更新 README 对应章节 → `git add README.md` → 与代码**同一次提交**（功能 commit 或 `docs(readme):` 前缀）。
   - **一致** → 直接提交，不碰 README。
4. 项目还没有 README.md 时：首次初始化就创建，描述初始功能与用法。

## 更新原则

- 只描述**当前实际实现**，不写规划中/未完成的功能。
- README 更新与功能代码同一次提交，保证文档与代码同历史、同可追溯。
- README 改动随 feature/release/hotfix 流程走，不单独开分支、不绕过红线。

## 常见的「不更新」借口（都是违规）

| 借口 | 现实 |
|---|---|
| 「这次改动很小，不用更新 README」 | 小改动也可能改变功能描述；判断标准是「描述是否与实际不一致」，不是改动大小 |
| 「README 之后再补」 | 之后一定会忘；必须与代码同一次提交 |
| 「我只看代码，文档是小事」 | README 是项目门面，功能变化不同步 = 文档失真 |
| 「这是内部实现，用户不关心」 | 只有重构（对外行为不变）才豁免；功能/接口/配置变化都要同步 |
| 「用户没让我更新 README」 | README 同步是提交流程的一部分，不需要额外指示 |
