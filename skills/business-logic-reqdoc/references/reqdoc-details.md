# ReqDoc 执行细则

> SKILL.md 骨架的配套。把「先核后写、零实现标识、两类前提、写完自查」落到每一步可执行。

## 0. 管什么

输入：某块现有系统/代码。输出：① 面向业务方评审、能指导其他 AI 在自己项目实现的需求文档；② 同目录《一致性核对底稿》（内部核对用，含代码标识）。**本技能讲业务契约，不讲旧代码结构；用户没说清的不许当成品交。**

两条产出红线：
1. **零实现标识**：交付文档不出现原代码的字段名/变量名/类名/方法名/枚举代码值/文件名/接口路径/表名/索引名/框架名/配置键——它们会误导实现方照抄旧结构。
2. **可实现性**：每条需求都是「业务上谁在什么条件下做什么、结果与异常如何」的契约；别的 AI 不看原代码、不按原结构，也能在它自己项目落地。

## 1. 需求明确门 · 问边界

### 1.1 最小边界集 4 问（动笔前至少问完，逐条记「问题 → 拍板答案」）
1. **用途与读者**：给谁看、干什么用？业务评审 / 验收 / 开发基线 / 指导别的 AI 实现——先给推荐答案。
2. **范围**：抽哪个功能/模块？子功能逐项确认纳入/排除（例：抽询价时，优惠券、积分、过期处理要不要一起）。
3. **端与角色**：前台 / 供应商端 / 后台端各要不要？覆盖哪些角色与权限？
4. **聚焦与已知**：只聚焦某场景吗？用户已知的缺口、已知与代码不一致的地方先说出来。

### 1.2 质询节奏
- 一次一问，等回答再问下一个；每问先给推荐答案 + 理由；用户回「你定」也要复述确认。
- **代码能答的不问**：先去查代码，查不出来再问人。
- 术语与项目文档（CONTEXT / 白皮书 / 模块文档）冲突 → 先指出再对齐。
- 每条结论原样进「与用户确认记录」；带 [ ] 未决项进「待确认」，附业务事实证据。

### 1.3 范围定了之后按需补问
- 历史数据：存量数据在新规则口径下是否都合法？有无需标注的历史脏数据。
- 兼容/发布：现状里已存在的灰度、开关、新旧并存要如实记录（业务语言描述）。
- 非功能现状：唯一性/幂等/并发在代码里怎么保证 → 转成业务约束（如「系统层保证同一 X 只存在一个 Y」），不写实现手段。
- UX 现状：加载态、空态、成功反馈、失败反馈、权限不足、网络异常、二次确认、按钮禁用条件——先查前端代码，问不出来才问人。

## 2. 前提门 · 前提识别

**每条前提 = 触发条件**：在什么情况下这个操作才成立/才被允许。问 + 取证双通道。

### 2.1 六类前提（抓取后一律转成业务语义）
| 类别 | 抓什么 |
|------|--------|
| 状态前提 | 仅「草稿」可提交；仅「待报价」可报价；仅「已报价」可确认；报价全失效回到「待报价」 |
| 身份/资质/权限 | 供应商须通过认证；被拉黑不能报价；会员等级达门槛才享权益；角色权限与数据范围 |
| 数据前提 | 至少 1 条明细；数量为正整数；金额 > 0 且 ≤ 预算上限；招标型询价必须上传规格书 |
| 配置/开关 | 阈值、功能开关、限额、可配置规则与取值范围 |
| 时间前提 | 报价有效期（如 7 天）、超时自动失效、时区/工作日历口径 |
| 外部依赖 | 第三方认证、消息通知、外部服务；失败/超时/重试的业务表现 |

取证位置：后端状态守卫与校验、权限中间件、DB 迁移唯一约束/CHECK/外键、配置文件、定时任务、前端按钮显隐与表单校验、测试用例。
产出：每条前提 → 业务语义表述 → 出处（底稿）→ 是否已确认。

### 2.2 两类前提（写作时别混）
- **业务操作前提（现状守卫）**：现在系统要求什么才允许操作 → 写进规则触发条件、交互流程「前置」、状态机。
- **实现前提（落地依赖，给实现方）**：别的项目要落地本需求必须具备什么业务概念/数据/能力 → 单列「实现前提条件」章节（写法见 §6）。

## 3. 一致性门 · 取证与核对

### 3.1 取证四层（缺一不可；用户说「逻辑都在后端」也要核前端）
- 前端：页面/组件、写死文案与促销横幅、表单校验（常与后端不一致，分开记）、按钮显隐与禁用、路由守卫、loading/空态/错误展示、i18n。
- 后端：业务处理、校验与状态机、参数与权限、定时任务/队列/事件、事务与锁。
- 数据库：迁移历史、唯一约束/CHECK/外键/级联/默认值、软删与审计。
- 隐性来源：测试用例、错误文案、配置文件、注释与 TODO、埋点、接口契约。

### 3.2 追踪完整旅程
用户动作 → 前端操作/校验 → 页面状态 → 请求 → 后端规则/状态流转/外部协作 → 数据库 → 响应 → 前端更新与用户可见结果。每步记**业务含义**。

### 3.3 业务事实卡片（底稿原料，不进交付文档）
> 业务描述 / 触发条件 / 结果 / 证据（文件:行、接口、表、测试——只进底稿）/ 硬 or 软约束 / 是否存疑

### 3.4 不一致处理协议（不猜、不改、不忽略）
- 典型：前端文案 vs 后端规则（横幅满200 vs 后端满300）；不同层守卫不一致；代码 vs 用户口头描述不一致。
- 处理：列「不一致点 + 双方业务事实 + 推荐答案」→ 问用户拍板 → 核实后文档写「以 XX 为准」。
- 绝不：擅自按一侧改写、把矛盾悄悄抹平、把「没核」当「一致」。

### 3.5 正/反向溯源（在底稿）
- 正向：文档每条需求 → 反查到代码证据。
- 反向：代码承载的每条业务行为 → 文档有对应章节。
- 底稿文件头注明「含代码内部标识，仅供一致性核对，禁止并入需求文档正文」。

### 3.6 代码里没有的功能
- 现状需求文档**不收录**（例：无实现的「二次报价」）。用户坚持要 → 指出这是新增需求，应走 `business-logic-improve`；在「后续建议」留一行，不展开。

## 4. 需求拍板 · 起草门槛

- §1 待确认 + §3 不一致点收敛成「拍板清单」逐条问用户。
- 有未决项时，交付物状态只能 = 「待确认」/「草稿」，并如实上报数量与证据。
- 用户不在场 → 停下等回复，不把未拍板项攒到交付后一次性甩给用户。

## 5. 零标识写作与可实现性

### 5.1 黑名单（正文禁止）
字段名、变量名、类名、方法名、函数名、枚举代码值（'Draft'/'Submitted'）、状态码字符串、文件名/路径、接口路径与 HTTP 动词、表名、索引名、约束名、框架/库名、配置键名。→ 只允许出现在《一致性核对底稿》。

### 5.2 ✗→✓ 对照
| ✗ 误导写法（禁止） | ✓ 业务契约写法 |
|---|---|
| 仅当 status='Draft' 可提交 | 询价单只有处于「草稿」状态时才能提交，提交后进入「待报价」 |
| 表 quote 唯一索引 idx_quote_unique(inquiry_id, supplier_id) | 同一询价单对同一供应商全局只允许存在一次报价，由系统层强制保证 |
| supplier.auditStatus !== 'Certified' | 未通过平台资质认证的供应商不能报价 |
| calcDiscount 满 300 减 20（inquiry-service.ts:12） | 报价金额满 300 可用 20 元满减，每单最多一张（出处只进底稿） |

### 5.3 可实现性自问（对每条规则）
读文档的 AI 不看原代码，能否确定：**谁触发 / 什么条件下成立 / 成功结果 / 失败与例外表现 / 与其它规则怎么联动**。缺一项就补。
- 业务对象用通用业务名 + 一句话定义（询价单 = 买方一次性采购需求的单据）。
- 状态/动作用业务语义词，给出完整状态机与每步守卫。
- 把「系统层保证 X」写成业务约束；实现手段留给实现方选。
- 不写原项目的模块划分/表设计/接口风格。

### 5.4 正文其它要求
- 硬/软约束标注：「金额必须 > 0」硬；「建议备注 ≤ 200 字」软。
- 状态机完整：每状态 × 每事件 → 目标状态，覆盖异常支线（超时/作废/驳回/并发冲突）；无流转写「无」。
- 用户动作四类结局：怎么操作 / 触发什么 / 成功展示 / 失败展示（校验·业务·权限·系统分列）。
- UX 状态逐项：加载/空/成功/失败/权限不足/网络异常/二次确认/按钮禁用——现状没有的写「无/不适用」。
- 不确定性如实记录：「此处行为依赖 XX 配置，需用户确认」，不许省略成「待定」。
- 影响面牵动其它模块用 [[模块id]] 互链（如有白皮书体系）。

## 6. 实现前提（落地依赖）怎么写

单列一章，写给实现方：**要实现这份需求，目标项目必须具备（或提供等价物）什么**。每条含「为什么必须 + 缺失时的对策」：

| 类别 | 写什么 |
|------|--------|
| 业务概念依赖 | 账号与企业认证、材料/商品目录与上架状态、供应商与认证、后台角色权限点……对应哪些 R 规则 |
| 数据前提 | 业务编号唯一生成与防重口径、存量数据状态映射（如有旧数据） |
| 能力前提 | 通知/消息渠道（需求含推送/文案回复时）、审计与时间记录、金额精度与币种约定 |
| 非功能前提 | 并发防双成交/重复报价、幂等；现状已有缺口处显式标为改进点，不冒充已实现 |
| 可自选边界 | UI 框架、表/字段设计、接口风格、权限点命名、消息实现方案属实现方可自选，**不构成前提** |

## 7. 自查清单与完成标准（收尾前逐项 ☑，有 ✗ 不收尾）

- [ ] 最小边界集已问完，「与用户确认记录」在案
- [ ] 前提逐条列出（业务语义）并有出处（底稿）与状态
- [ ] 前端 + 后端 + 数据库 + 测试均已取证
- [ ] 不一致点已列出并处置（拍板或「以 XX 为准」），无「没核当一致」
- [ ] 每条需求可正向溯源、代码业务行为已反向覆盖（底稿）
- [ ] 分组自查 ☑ 或标「不适用 + 原因」：数据层 / 接口层 / 业务规则层（含状态机异常支线）/ 前端层 / 集成层 / 安全合规 / 边界异常（并发·时区·精度·超时）/ 测试覆盖 / 注释文档 / 规格质量
- [ ] **标识扫描通过：正文零实现标识**（字段/变量/类/枚举代码/文件名/接口路径/表名/索引名一个都没有）
- [ ] 可实现性抽查：每条规则「谁触发/条件/结果/异常/联动」齐全，脱离原代码可落地
- [ ] 「实现前提」章节已写：四类依赖逐条含缺失对策；技术选型未被误当前提
- [ ] 待确认项带证据；文档状态如实（草稿/待确认/已核对）
- [ ] 《一致性核对底稿》已生成，文件头注明仅内部使用
- [ ] 输出路径/命名正确；有白皮书体系时登记关联
- [ ] 用户复核后才标「已核对」；点头前不宣称完成

## 8. 输出与收尾

- 交付物一：`docs/business-logic/requirements/<日期>-<业务名>-需求文档.md`——纯业务语言、零实现标识。
- 交付物二：同目录 `<日期>-<业务名>-一致性核对底稿.md`——正/反向溯源 + 分组自查 + 代码证据。
- 仓库没有 `docs/business-logic/`：先问用户落点。
- 汇报五件事：① 已确认边界/前提 ② 与代码的不一致点及处置 ③ 待确认问题（带业务证据） ④ 自查结论 ⑤ 核对底稿路径。
