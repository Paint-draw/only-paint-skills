# 现状业务 → 需求文档（ReqDoc）

把系统里「已经实现、正在运转」的业务逻辑，翻译成 **业务方能看懂评审、且其他 AI 能站在它自己项目角度直接实现** 的需求文档。

产出的是**业务契约**，不是旧代码的结构说明书：谁在什么条件下做什么、结果与异常如何表现、需要哪些业务概念与能力做前提。读者看完应能判断「这套系统现在到底怎么跑」，而不是「原来那套系统用什么字段/表/接口写的」。

> 本文件是骨架。可执行细节（必问清单、前提识别清单、取证核对协议、零标识写作规范、自查清单）在 `references/reqdoc-details.md`；交付文档模板在 `assets/需求文档.template.md`。全部自包含，不依赖外部技能。

## 家族分工：我是哪一环

| 用户的诉求 | 该走谁 |
|---|---|
| 把现有功能/代码整理成**需求文档**，给人评审 + 给别的 AI 实现 | **本技能** |
| 完善 / 优化 / 改造业务逻辑，出完善文档 + 实施计划 | `business-logic-improve` |
| 抽「技术无关、可重实现」的规格（换栈 / 迁移复用） | `business-logic-extractor` |
| 项目没有白皮书体系，要建立业务文档库 | `business-logic-init` |
| 手上有计划文档，要把计划落地成代码 | `business-logic-execute` |

边界在哪：本技能只写**现状事实**（代码里已有的业务行为）。用户想要的新功能、改进项，属于 improve 的活，可以在文档「后续建议」留一行，不展开、不写进现状正文。

## 为什么是这几条铁律（错了返工的代价最大）

1. **边界不清就不动笔。** 抽哪个功能、给谁看、含哪些端、排除什么——没确认就写，文档必然失真返工。动笔前至少跑完「最小边界集 4 问」（见 §1）。
2. **前提没确认就动笔 = 把猜测当事实。** 每条业务规则能成立都有前提（状态、资质、数据、配置、时间、外部依赖）。前提分两类，都要写：①业务操作前提——现在系统要求什么才允许这个操作；②实现前提——别的项目要落地这份需求，它自身必须具备什么。
3. **没核代码就写 = 生产谣言。** 前端文案、后端规则、数据库约束三处说法不一致是常态（例：前端横幅「满200减20」vs 后端算「满300减20」）。**前端 + 后端 + 数据库 + 测试缺一不可**；不一致就列出来问用户，不猜、不改、不悄悄抹平。
4. **用户需求没明确就不交定稿。** 用途、范围、读者没拍板，只能交「工作草稿 + 待确认问题清单」，文档状态如实标「草稿 / 待确认」。
5. **正文零实现标识。** 字段名、变量名、类名、方法名、枚举值、接口路径、文件名、表名、索引名一律不进交付文档——它们会误导读者照抄旧项目结构，而目标项目的表/字段/代码完全不同。代码证据只进同目录的《一致性核对底稿》。
6. **自查不过不收尾。** 每条需求能反向找到代码证据、代码每条业务行为在文档里有章节、正文过一遍「标识扫描」；过不了就改到过为止。

## 工作流（六步，先核后写）

### 0｜问边界与需求（先于一切）
- 一次一问，每问**先给推荐答案 + 一句理由**；代码能答的问题先去查代码，查不到才问人。
- 最小边界集 4 问：① 用途与读者（业务评审 / 验收 / 开发基线 / 指导别的 AI 实现）② 范围（哪个功能模块，纳入 / 排除逐项列）③ 端与角色（前台 / 供应商 / 后台……）④ 已知缺口与不一致（用户已知的先说出来）。
- 每问结论原样记「问题 → 拍板答案」入文档确认记录；没回应的进 [ ] 待确认清单，带证据。
- 用户催稿 / 说别问了：说明省略的后果，但**至少跑完最小边界集**才动笔；用户不在场就停下等回复，不许把一堆未拍板项攒到交付后甩给用户。

### 1｜取证（代码 → 业务事实卡片）
- 扫四层，缺一不可：**前端**（页面 / 写死文案与促销横幅 / 表单校验 / 按钮显隐 / 状态展示）、**后端**（业务处理 / 状态机 / 校验 / 定时任务 / 权限）、**数据库**（迁移里的唯一约束 / CHECK / 外键 / 默认值 / 软删）、**测试与配置**（测试揭示的边界行为 / 配置开关 / 错误文案）。
- 挑一个真实用户动作，追踪完整旅程：操作 → 前端校验 → 请求 → 后端规则与状态流转 → 数据库 → 结果回前端 → 用户看到什么。
- 每一条业务事实记成「事实卡片」：业务描述 / 触发条件 / 结果与例外 / 硬 or 软约束 / 代码出处（仅供底稿）/ 是否存疑。

### 2｜一致性核验（抽离结果 vs 代码）
- 同一行为在不同层表述不一致（金额阈值、状态门槛、资格校验最常见）→ 列「不一致点 + 双方业务事实 + 推荐答案」问用户拍板，核实后文档写「以 XX 为准」。
- 代码里不存在的行为（例：用户提过的「二次报价」没实现）**不得写进现状正文**。
- 正/反向溯源留在底稿：每条需求 → 能找到代码证据；每段代码业务行为 → 文档有对应章节。

### 3｜需求拍板（不拍板不产定稿）
- 把 §0 的待确认项 + §2 的不一致点收敛成一份「拍板清单」逐条问用户。
- 拍板结果原样填回文档「与用户确认记录」。仍有未决 → 文档状态只能 = 待确认，交付时如实上报数量。

### 4｜起草（双交付物）
- 交付物一（正文）：按 `assets/需求文档.template.md`，**只写业务语言**。业务对象用业务名 + 一句话定义；状态用业务语义（草稿 / 待报价 / 已报价…）；规则写成「谁触发 / 何时成立 / 结果 / 例外」的契约。
- 两类前提都写：操作前提落在规则触发条件与状态机；**「实现前提条件」单列一章**（业务概念依赖 / 数据前提 / 能力前提 / 非功能前提，每条含「为什么必须 + 缺失时的对策」，见 references §6）。
- 交付物二（内部核对）：同目录《<日期>-<业务名>-一致性核对底稿.md》，文件头注明「本底稿含代码内部标识，仅供一致性核对，禁止并入需求文档正文」。
- 输出位置：`docs/business-logic/requirements/`（仓库无该目录先问用户落点）。

### 5｜自查（不过不收尾）
- 标识扫描：通读正文，凡字段名 / 变量名 / 类名 / 方法名 / 枚举代码值 / 文件名 / 接口路径 / 表名 / 索引名 → 删或改写为业务语义（证据可移入底稿）。
- 反向覆盖：代码承载的每条业务行为在正文都有对应章节（对照底稿反向表）。
- 可实现性抽查：对每条规则问「别的 AI 不看原代码，能否确定谁触发 / 什么条件下成立 / 结果 / 异常 / 与其它规则怎么联动」，缺就补。
- 过 `references/reqdoc-details.md` §7 的自查清单，逐项 ☑ 或标「不适用 + 原因」。
- 专项核对：前提条件、状态机异常支线、空 / 加载 / 错误态、重复提交 / 并发 / 超时。

### 6｜交付与汇报
- 汇报五件事：① 已确认的边界与前提　② 与代码的不一致点及处置　③ 待确认问题（带业务证据）　④ 自查结论　⑤ 核对底稿路径。
- 文档状态流转：草稿 → 用户拍板 → **已核对**。用户点头前不宣称完成。
