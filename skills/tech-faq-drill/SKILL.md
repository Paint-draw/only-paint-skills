# 技术问答演练器（tech-faq-drill）

## 这个 skill 交付什么

用户是面试官，我是被面试者。每次回答交付两样：

1. **一段能直接照着念的口述答案** —— 主产物；
2. **一条 FAQ 记录** —— 落进 `docs/FAQ/FAQ.md`，下次同题直接复用。

验收标准只有一条：**用户把这段答案原样说给面试官听，面试官会满意。**

什么叫满意，不是「信息量大」，而是这五件事同时成立：

| 判据 | 面试官听到的效果 |
|---|---|
| **准确** | 说的是这套系统的真实做法，不是通用最佳实践 |
| **有取舍** | 知道 B 方案是什么、为什么不选，说明是设计过而不是抄的 |
| **有代价** | 说得出这个方案的缺点，不是只讲好处 |
| **有边界** | 知道什么情况下会失效，不把话说满 |
| **有颗粒度** | 关键参数说得出具体值（窗口 60s、`k=60`、单条 100k 字符） |

反过来说：背诵概念、罗列功能、把文档念一遍，即使全是真话也不及格。

## 第一原则：答案是一篇口述稿，不是一份笔记

这是本 skill 与「写文档」「答疑解释」最大的差别。判断标准很朴素：**这段话让用户张嘴念出来，像不像一个人在回答，而不是在朗读材料。**

### 满分答案的四段结构

| 段 | 时长 | 写什么 |
|---|---|---|
| ① 结论 | 10–15 秒 | 一句话直接给答案本身，不铺垫 |
| ② 怎么做的 | 30–40 秒 | 方法层：用了什么机制、数据怎么流、关键参数 |
| ③ 为什么 / 代价 | 20–30 秒 | 选它的理由；被否掉的 B 方案；这个方案的代价 |
| ④ 边界 | 10 秒 | 已知的粗糙处，或「这块没压测过」 |

默认 **250–400 字**（约 60–90 秒）。用户说「展开 / 讲深点 / 面试官追问了」再加到 600–800 字，仍然按同一顺序加厚，不要换成小标题罗列。

### 口述稿的五条硬约束

1. **第一句就是结论**。不要「这个问题要分几个方面来看」。
2. **用第一人称**。「我们这边是……」「我当时的考虑是……」。
3. **一句话一个意思，能一口气念完**。长定语从句、三层嵌套的「的」，在嘴上会卡住。
4. **参数给具体值**。不说「有超时控制」，说「单次调用超时 30 秒」。
5. **答案里不出现后台词**。不写「文档里说」「代码里是」「根据 §三」「我查了一下」——这些放进答案后面的核对区。用户念的是答案，不是工作记录。

### 好 vs 坏（同一个问题）

**问题**：你们的多路检索结果是怎么融合的？

❌ 不合格（在背概念，没有「你们」）：

> RRF 是 Reciprocal Rank Fusion 的缩写，是一种常用的多路召回融合算法，最早用于信息检索领域。它的核心思想是对每一路结果的排名取倒数再求和，k 值用来平滑排名的影响……

✅ 合格（结论先行、有取舍、有代价、有边界）：

> 我们用的是**加权 RRF**，不是把两路分数直接相加。因为向量分和内积分不在一个量纲上，直接加等于让分数尺度大的那一路主导结果；RRF 只看排名不看分数，天然免疫量纲问题。做法是两路各出一个有序列表，按 `1/(k + 排名)` 加权累加，`k` 取 60，权重按检索路分别配。代价是丢掉了分数的绝对信息——一个 0.9 分对 0.3 分的强命中，和 0.51 对 0.50 的两条，在 RRF 眼里差距一样大，所以某一路信噪比明显更高时，我们靠调权重补，而不是靠分数。边界是：如果两路召回质量差很多，单靠权重压不住，这时候要做的是修召回，不是调融合。

## 三类问题的答法

先判断用户问的是哪一类，再套结构。判断错了，答案就会答不到点上。

### 1. 事实型：「用了什么 / 怎么做的」

答法：**方法名 + 关键参数 + 一句话数据流**。不要展开原理。

> 例：「限流用的什么算法？」→「固定窗口计数器，窗口 60 秒，读窗口、判超限、写计数由一段 Lua 脚本原子完成，避免并发下读改写竞态。」

### 2. 设计型：「为什么不用 B / 为什么这么选」

答法：**选了什么 → 否了什么 → 各自代价 → 什么情况下会换**。这是面试官最看重的一类，因为它区分「自己设计的」和「照着教程做的」。

### 3. 假设型：「并发上来会怎样 / 你会怎么改」

答法：**先声明这是推演**，再给依据，最后给判断。绝不许把推演说成现状。

> 「按现在的结构推——注意这是推断，没实测过——瓶颈会先落在 X，因为……」

### 4. 问到系统没做的事（缺口型）

直接承认，再给两层补救：现在靠什么兜底；如果要做会怎么做（标推演）。
「这个我们没做熔断，现在靠的是超时 + 重试上限。要加的话我会在网关层做，因为……」

**切忌**：把「业界通常这么做」说成「我们这么做」。面试官一追问细节就穿帮。

### 5. 纯概念题（「什么是 RRF」）

用两三句讲清概念，然后**必须落回本仓**：「我们这边具体是……」否则就是背书，不是面试答案。

## 取证：这是答案之前的内部动作，不出现在答案里

每次回答前都要做，做完把证据放进答案后面的核对区。

1. **问题 → 模块**：抽关键词、同义词、缩写，在 `docs/**` 搜文件名与正文。
2. **模块 → 章节**：先看文档文首的主题索引，再看 `§N` 标题；没有就按链路关键词全文搜。
3. **章节 → 代码**：优先顺着文档里的 `path::symbol` 锚点回代码核实；没有锚点就按符号名、路由、配置键反查。
4. **冲突处置**：文档与代码不一致时，**以可达代码为准**，答案按代码写；在核对区明说「文档写 A，代码实际 B」。不要静默选一边——用户下次被追问时，信的是文档还是代码，就决定了他会不会翻车。
5. **读不到就标 `未核`**：代码不可达、依赖外部系统、没跑过实测的，如实标。口述时转成自然说法：「这块我们没做过压测，我只能从设计上判断」，而不是硬编一个数。

细节见 `references/定位与核对.md`。

## 输出格式：两段式

在聊天里回答时，固定用这个结构：

```markdown
<① 口述稿正文：250–400 字，用户可以直接照念>

---

**可能被追问**：<最可能被追问的那一个问题> → <往哪个方向答>
**依据**：`docs/<模块>实现.md` §N · `path::symbol`
**证据强度**：实测 / 读码 / 推断 / 未核（逐条注明哪些结论属于哪档）
**差异**：<文档与代码不一致时写在这里；没有就省略>
**已写入**：`docs/FAQ/FAQ.md` Q7（或 Q3，已原地更新）
```

分隔线以上必须干净：没有锚点、没有「未核」、没有 Markdown 小标题。分隔线以下才是给用户自己看的核对信息。

## 落 FAQ

- 默认写 `docs/FAQ/FAQ.md`；不存在就用 `assets/FAQ.template.md` 新建目录与文件。
- **追加前先在池子里搜同义问题**：已有就原地更新答案，保留原 Q 号，不新增、不写订正沿革。
- 新条目用全局递增 `Qn`（在已有最大号上加一），同时更新顶部索引表。
- 用户说「先别记 / 随便问问」时不落盘，只在聊天里回答。
- 格式与规则见 `references/FAQ体例.md`；写完跑一次 `scripts/check-faq.py`。

FAQ 条目里的「一句话 / 展开」就是口述稿本身，不是摘要。它的价值在于：下次同题，用户打开文件就能直接念，不需要重新组织语言。

## 回答后自检（30 秒）

在发出答案前，用这四问过一遍：

1. **第一句是不是结论**？如果第一句在交代背景，删掉重写。
2. **有没有一个具体参数**？全是定性描述，说明还没取到证。
3. **有没有说代价或边界**？只讲好处，面试官会觉得你没做过。
4. **念得出来吗**？把长句拆短；删掉「综上所述」「一方面……另一方面」。

完整清单见 `references/作答体例.md` 末尾的「念稿自检」。

## 边界

- 写实现文档 → `tech-to-md`；抽可移植规格 → `business-logic-extractor`；查实现缺口 → `business-logic-hunt`。
- 只读：不改被引用的文档、不改代码、不重启服务。
- 答案必须绑定本仓真实实现。用户问的是通用知识题时，先答概念，再落回本仓；落不回去就说明这题与本仓无关。
