# 作答体例

> **本文的示例只示范「结构与语气」，其中的参数、结论一律不可照抄。**
> 实际作答时以当次取证为准——示例里的数字是编的，照抄会当场翻车。

---

## 一、面试官在听什么

一个满意的面试官，听完一段回答后心里会过五关。任何一关不过，印象都会打折：

| 关 | 他心里在想 | 对应写法 |
|---|---|---|
| 1 | 这是你们的做法，还是通用答案？ | 全程第一人称，讲本仓的具体机制 |
| 2 | 是他设计的，还是照抄的？ | 说得出 B 方案和为什么不选 |
| 3 | 他知道代价吗？ | 主动说这个方案的缺点 |
| 4 | 他知道边界吗？ | 说清楚什么情况下会失效 |
| 5 | 他经得起追问吗？ | 每个关键结论都有锚点或实测 |

**结论**：一段好答案的信息密度不在于「说了多少」，而在于「每一句都经得起下一问」。

## 二、四段结构

### ① 结论（10–15 秒，1–2 句）

直接回答被问的那件事。句式模板：

- 「我们用的是 **<方法名>**，不是 **<最容易被误认为的做法>**。」
- 「这块的核心是 **<一句话机制>**。」
- 「这个我们没做，现在是靠 **<兜底手段>** 撑着的。」

**禁止**：以「这个问题要分几个方面」「首先我需要说明背景」开头。

### ② 怎么做的（30–40 秒，3–5 句）

只写方法层，按数据流讲：

```
谁触发 → 做了什么处理 → 落到哪 / 传给谁 → 输出什么
```

要求：
- 至少一个**具体参数**（窗口长度、超时时间、批量大小、`k` 值、字符上限）。
- 说清**数据形状**：传的是 `{a, b, c}` 这样的结构，不是「一个对象」。
- 不出现函数名、变量名、行号，除非它本身就是契约（请求字段、配置键、表名）。

### ③ 为什么 / 代价（20–30 秒，2–3 句）

固定三件事：

1. 为什么选它（解决什么问题）；
2. 否掉了什么（B 方案 + 它的代价）；
3. 这个方案自己的代价。

> 「没选 B 是因为 B 要 X，而 X 在我们这儿代价太大。但 A 也不是白拿的，它的代价是 Y。」

如果确实没有 B 方案（硬约束），直接说硬约束是什么，别硬编一个。

### ④ 边界（10 秒，1 句）

二选一：

- 已知的粗糙处：「已知的问题是……，影响范围是……」
- 没验过：「这块我们没做过压测 / 没在真实流量下验过，所以只能从设计上判断。」

**主动亮边界不会减分，被追问出来才会。**

## 三、五类问题

### 3.1 事实型 —— 「用了什么 / 怎么做的」

**骨架**：方法名 → 关键参数 → 一句话数据流 → （可选）一句代价。

**示例（结构示意）**：

> 我们做的是**固定窗口限流**。每个 key 按 60 秒切一个窗口，请求进来先读当前窗口的计数，超了就拒，没超就把计数加一——读、判、写这三步在一段 Lua 脚本里原子完成，所以并发下不会出现「都读到 9，都以为没超」的竞态。窗口边界会有突刺，这是固定窗口的固有代价，我们接受它，因为这里要的是粗粒度保护，不是精确配额。

**常见失误**：把「用了 Redis」「用了 Lua」当成答案。工具不是方法，**拿它做了什么**才是。

### 3.2 设计型 —— 「为什么不用 B」

**骨架**：选了什么 → B 的问题 → 各自代价 → 什么情况下会换。

**示例（结构示意）**：

> 我们用**加权 RRF** 而不是分数直接相加。原因是两路分数不在一个量纲，直接加等于让尺度大的那一路主导；RRF 只看排名，天然免疫这个问题。代价是丢掉分数的绝对信息——0.9 对 0.3 的强命中，和 0.51 对 0.50，在 RRF 眼里一样。所以如果某一路信噪比明显更高，我们靠调权重补，而不是回头用分数。如果哪天某一路的召回质量崩了，权重是压不住的，那时候要修的是召回，不是融合。

**加分点**：最后那句「什么时候这个选择会失效」。它证明你理解方案的前提，而不只是记住结论。

### 3.3 假设型 —— 「并发上来会怎样 / 你会怎么改」

**骨架**：声明这是推演 → 给依据 → 给判断 → 给验证方式。

> 「先说清楚，这是推断，没压测过。按现在的结构，瓶颈会先落在 X，因为每一次请求都要……。如果要验，我会先压 Y 这条路径，看 P99 和队列深度。」

**绝对禁止**：把推演说成现状（「我们扛得住十万并发」）。

### 3.4 缺口型 —— 「你们有熔断吗」

**骨架**：直接承认 → 现在靠什么 → 要做会怎么做（标推演）。

> 「没有做熔断。现在靠的是调用超时加上游重试上限，最坏情况是一个慢依赖把线程池拖住，靠超时兜底。要加的话我会放在网关层做，因为那里的调用边界最清楚；放在业务层会导致每个依赖各写一套。」

**承认缺口不丢分，含糊其辞才丢分。**

### 3.5 概念型 —— 「什么是 RRF」

**骨架**：两三句概念 → 立刻落回本仓 → 「我们这边的具体做法是……」

> 「RRF 是按排名融合，不看原始分数，每路按 1/(k+排名) 累加，避免不同来源的分数量纲打架。我们这边是两路召回各出一个有序列表，加权之后合并，k 取 60。」

**禁止**：讲完概念就停。面试官问概念，往往是在给机会让你讲自己的实现。

## 四、口述语言规范

### 4.1 该这样说

| 场景 | 写法 |
|---|---|
| 讲机制 | 「请求进来先……然后……最后……」 |
| 讲取舍 | 「没选 B，因为 B 要……；A 的代价是……」 |
| 讲参数 | 「超时 30 秒」「`k` 取 60」「单条上限 100k 字符」 |
| 讲不确定 | 「这块没压测过，只能从设计上判断」 |
| 讲边界 | 「已知的问题是……；正常路径不受影响」 |

### 4.2 不该这样说

| 反面写法 | 为什么不行 | 改成 |
|---|---|---|
| 「文档里写的是……」 | 后台词，破坏面试感 | 直接说事实，出处放核对区 |
| 「根据代码，第 42 行……」 | 同上，且像在念代码 | 说机制，不说行号 |
| 「应该是……」 | 把推断说成事实 | 「按这个结构推……，没实测」 |
| 「业界通常……」 | 答的是通用知识，不是你们 | 「我们这边是……」 |
| 「采用了先进的……」 | 形容词不承载信息 | 说它具体解决了什么 |
| 「一方面……另一方面……」 | 书面腔，口头卡顿 | 拆成两句短句 |

### 4.3 句子长度

一句控制在 **25–35 个汉字**。超过 40 字就拆。判断方法：自己在心里念一遍，需要换气的地方就是该断句的地方。

### 4.4 数字的口径

参数必须带口径，不能只给数字：

- ❌「窗口是 60」 → ✅「窗口 60 秒」
- ❌「上限 100k」 → ✅「单条工具结果上限 100k 字符」
- ❌「k 是 60」 → ✅「RRF 的平滑常数 k 取 60」

## 五、证据的自然表达

内部有四档证据强度，但**口述时不能把「未核」两个字念出来**——那会让面试官觉得你在交作业。转成自然说法：

| 内部档位 | 口述说法 |
|---|---|
| 实测 | 「我们压过 / 跑过，……」 |
| 读码 | 正常陈述即可，不必声明来源 |
| 推断 | 「按这个结构推，应该……，不过没实测过」 |
| 未核 | 「这块我们没专门验过，我只能从设计上判断」 |

核对区（分隔线以下）仍然如实标四档，那是给用户自己看的。

## 六、常见失误清单

- [ ] **答成文档摘要**：按文档章节顺序讲，而不是按对方的问题讲。
- [ ] **答成概念科普**：讲了三分钟 RRF 原理，没讲一句自己的实现。
- [ ] **只有好处**：全程「这样更优雅 / 更高效」，没有一句代价。
- [ ] **参数缺失**：全是「有超时」「有限流」，没有一个具体值。
- [ ] **把注释当事实**：注释写「这里做了校验」，实际代码没做。
- [ ] **把文档当事实**：文档描述的是上一版行为。
- [ ] **过度声称**：「十万并发没问题」，实际没压过。
- [ ] **答非所问**：问了「为什么」，答了「是什么」。
- [ ] **长句套长句**：念到一半自己都不知道主语是谁。

## 七、念稿自检

发答案前，按顺序做四件事：

1. **默念第一句**。如果它不是结论，重写开头。
2. **数参数**。整段有没有至少一个具体值？没有就回去取证。
3. **找代价**。有没有一句在说这个方案的不好？没有就补。
4. **出声念一遍**（或在心里按语速过一遍）。卡住的地方就是长句，拆掉。

再加两问：

5. **如果面试官追问「为什么不用 B」，这段答得出吗？** 答不出说明取舍没挖到。
6. **如果追问「有没有验过」，这段会不会被拆穿？** 会的话，把话说软，或者去验。
