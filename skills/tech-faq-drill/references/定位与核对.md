# 定位与核对

> 一句话原则：**文档是索引，代码是事实。**
> 文档负责告诉你「去哪儿看、这块大概是怎么回事」，代码负责回答「现在到底是不是这样」。

---

## 一、从问题到模块

用户的问题不会自带模块名。先抽出三类词：

1. **领域词**：限流、检索、召回、重排、鉴权、工具调用、摄入、分块……
2. **专有名词**：RRF、LiteLLM、MCP、Nacos、pgvector、Celery……
3. **行为词**：「为什么这么慢」「超时了会怎样」「并发上来」「失败了怎么办」。

领域词决定**去哪份文档**，行为词决定**读哪一节**。

**同义词先扩一轮**，否则会在错误的文件里空转：

| 问题里的说法 | 先补搜这些写法 |
|---|---|
| 检索 / 问答 / 召回 | RAG、retrieval、recall、kb、知识库 |
| 限流 / 频率限制 | rate limit、throttle、配额 |
| 缓存 | cache、命中、TTL、失效 |
| 工具 / 插件 | tool、MCP、function call |

---

## 二、从模块到文档

搜索顺序（前一步命中就停，不要贪多）：

1. `ls docs/` 看文件名——多数实现文档的标题就是模块名；
2. 在 `docs/**` 全文搜模块关键词，找**章节标题**命中的那份；
3. 打开候选文档，先读**文首的主题索引表**（`# / 主题 / 位置`），按主题挑 `§N`；
4. 索引里没有，就全文搜行为词，定位到具体的 `§N.M`。

找到后记下三样：**文档路径、§N、那一节给出的代码锚点**。

> 找不到文档不等于没法答。见本文第七节。

---

## 三、从文档到代码

按可靠性从高到低：

1. **文档里的 `path::symbol` 锚点** —— 直接跳到符号，读它和它的调用者；
2. **配置键** —— 反查代码里的读取点与默认值；
3. **路由 / 事件名 / 表名** —— 反查注册点；
4. **行为关键词** —— 在源码里搜报错文案、日志字段、状态枚举。

读的时候只回答四个问题，多读的部分不算取证：

| 问题 | 为什么问 |
|---|---|
| 入参是什么形状？ | 决定层间数据怎么讲 |
| 出参 / 落库是什么形状？ | 决定输出怎么讲 |
| 副作用有哪些？ | 缓存、计量、审计往往藏在这里 |
| 失败时走哪一支？ | 边界与代价的来源 |

## 四、核对清单

文档里每一条要写进答案的结论，至少过一遍下面这几项：

- [ ] **符号还在吗**：文档提到的函数、类、表、配置键，在当前代码里存在且拼写一致。
- [ ] **调用点覆盖全了吗**：这个机制只在一个入口生效，还是所有入口都生效？文档常只写了主路径。
- [ ] **配置值是哪一层的**：代码默认值、环境变量 / 配置中心、数据库 seed，三者可能不同。**配置中心会静默压过代码默认值**，看到默认值别急着当实际值。
- [ ] **那一支可达吗**：注释说做了校验，但那个分支有条件永远进不去——先确认可达，再决定信不信。
- [ ] **数字是不是一次读数**：文档里的「当前是 N」可能早过期；能重算就重算，不能就标 `未核`。
- [ ] **是自研还是调库**：是你们写的逻辑，还是框架默认行为？这决定面试官追问时你该往哪答。

---

## 五、文档与代码冲突

这是本 skill 最需要守住的环节。

**处置顺序**：

1. 以**可达代码**为准写答案；
2. 在核对区写明差异：文档写 A，代码实际 B；
3. 判断差异**对使用者有没有影响**，有影响就在答案的「边界」段里带一句；
4. 不要静默选一边，也不要在口述稿里说「文档和代码不一致」——那是核对区的话。

**为什么不能静默**：用户面试时如果按文档说，而面试官恰好熟悉代码，一句追问就会露馅；如果按代码说，至少是站得住的。

**三种典型冲突**：

| 形态 | 处理 |
|---|---|
| 文档描述旧版本行为 | 按代码答，核对区注明「文档停留在旧口径」 |
| 文档写了设计意图，代码没实现 | 按代码答；把这个「意图未落地」放进边界段，往往是加分项 |
| 注释与代码不符 | 先确认那一支可达；按实际执行路径答 |

## 六、跨服务 / 跨栈问题

先问一句：**这条数据谁写、谁读？** 写入方是权威。

- 身份、租户、trace 这类隐式上下文：找出谁注入、经过哪几跳、漏了会怎样；
- 时间戳：不同存储可能一个存本地时间、一个存 UTC，比较前先确认基准；
- 同一份配置在多处各有一份：以**实际生效的那一份**为准（通常是启动时加载的那份）。

核不全就标 `未核`，不要用「应该会传过去」补空。

---

## 七、模块没有实现文档

照常回答，但要做三件事：

1. 答案完全来自读码，核对区标「读码」；
2. 在回答末尾提一句：「这个模块目前没有实现文档，答案全部来自读码；建议之后用 `tech-to-md` 补一份」；
3. 读码时尤其注意入口普查——没有文档时，最容易漏掉旁路入口。

---

## 八、时间预算

一个问题的取证控制在**合理一轮**内（大约读 3–8 个文件）。找不到就：

- 标 `未核`，说清「需要什么条件才能核」（例如「要跑一次压测」「要连真实库看数据」）；
- 不要为了凑一个答案去读半個仓库——读得越多，越容易把相邻模块的行为误当成这个模块的。

**取舍**：一个诚实标了 `未核` 的答案，比一个读了二十个文件还说不准的答案更有用。

---

## 九、七种常见假象

1. **文件名 ≠ 行为**：`retry.py` 里可能没有重试。
2. **注释 ≠ 代码**：注释写「已校验」，代码可能只校验了一边。
3. **默认值 ≠ 生效值**：配置中心会覆盖。
4. **降级 ≠ 成功**：降级分支返回空结果，看着像跑通了。
5. **入口 ≠ 唯一入口**：后台任务、定时任务、内部调用常常是第二条路。
6. **「没人调用」要先查三种形态**：裸名、别名、命名空间限定名，缺一种就可能假零。
7. **测试绿 ≠ 验到了**：断言可能恒真，或者只覆盖了成功路径。

---

## 十、把证据带进答案

取证结果最终只进两个地方：

- **口述稿**：只留方法和参数，不留出处；
- **核对区**：`依据` 写 `docs/<模块>实现.md` §N + `path::symbol`；`证据强度` 逐条标四档；有冲突写 `差异` 行。

**不要把整张证据表贴进回答**。它属于内部过程，贴出来只会稀释答案。
