# FAQ 体例

> 问答库是**长期追加的单一池子**，跨模块、不按模块分文件。
> 它只有一种用法：面试前翻索引，找到问题，直接念「一句话 + 展开」。

---

## 一、文件位置

```
docs/FAQ/FAQ.md
```

一个仓一份。第一次使用时用 `assets/FAQ.template.md` 新建目录与文件。

**为什么不按模块拆文件**：问题是想起来就问的，跨模块很常见；拆开之后，同一个问题会在两个模块下各有一半答案，而且索引也要维护多份。单文件 + 索引里的「模块」列已经够导航。

---

## 二、条目格式

```markdown
## Q12. <问题原文，用提问的口吻>

- **模块**：<模块名> · **类型**：事实 / 设计 / 假设 / 缺口 / 概念
- **依据**：`docs/<模块>实现.md` §N · `path/to/file.py::symbol`
- **证据强度**：实测 / 读码 / 推断 / 未核

**一句话**：<10–15 秒的结论，面试开场那句>

**展开**：<30–60 秒的方法层答案；短句、第一人称、带具体参数>

**可能被追问**
1. <下一层问题> → <简答>
2. <下一层问题> → <简答>
```

### 各字段的要求

| 字段 | 要求 |
|---|---|
| 标题 | 用**提问的口吻**，保留原始问法里的关键词，方便下次搜到 |
| 模块 | 与文档章节名一致；跨模块的写主模块 |
| 类型 | 决定答法（见 `作答体例.md` 第三节），不要五个都写 |
| 依据 | `docs/...` §N + `path::symbol`；不确定的锚点宁可不写，也不要写错 |
| 证据强度 | 用**实测 / 读码 / 推断 / 未核**四个词，多个结论分档的写成「机制：读码；参数：实测」 |
| 一句话 | 就是口述稿的第一段，不是摘要 |
| 展开 | 就是口述稿的②③④段，不是文档摘抄 |
| 可能被追问 | 1–3 条；每条给「问题 → 简答」，不单独成条 |

**「一句话 + 展开」合起来必须是一篇能直接念的口述稿。** 如果读起来像百科条目、像文档、像要点罗列，说明这一段没写好。

---

## 三、Q 号规则

1. **全局递增**：`Q1`、`Q2`……取当前文件里的最大号加一。
2. **永不复用**：删掉的条目也不把号让出来。
3. **永不重排**：编号是引用接口，别处可能引用「FAQ Q7」。
4. **一个条目一个问题**：复合问题拆成两条（「A 和 B 分别怎么做」→ 两条），并在拆分时把上下文的公共部分补全，保证每条能独立读懂。

---

## 四、索引表

固定在文件顶部，格式：

```markdown
| # | 问题 | 模块 | 依据 |
|---|---|---|---|
| Q1 | 限流为什么用固定窗口？ | 限流和缓存 | §二 · `...::...` |
```

规则：

- 表头固定为 `# / 问题 / 模块 / 依据` 四列，顺序不变；
- **与正文一一对应**：正文有几条，索引就有几行；不做只在一侧的条目；
- 问题列用短问法（可与标题略不同，但要能认出来）；
- 依据列写 `§N` 加符号即可，不必整段复制。

索引与正文不一致时，整个库就不可信了——所以每次落盘后跑 `scripts/check-faq.py`。

---

## 五、重复问题的处理

落盘前**必须先搜**。搜索方式：

- 搜标题里的关键词；
- 搜同义词与缩写（「融合」/「RRF」/「重排」）；
- 搜这个问题指向的文档 §N——同一节的条目大概率在讲同一件事。

**已有同义条目时**：

1. 保留原 Q 号；
2. 用新取到的证据**重写**「一句话 / 展开 / 依据 / 证据强度」；
3. 如果新答案推翻了旧答案，直接改，不写「原文如此，已订正为…」这类订正沿革——旧答案留在文件里只会误导下一次的自己；
4. 索引行同步更新。

**没有同义条目**才新增。

---

## 六、增量与失效

- 不写日期、不写批次、不写「本次补充」。
- 依据里的行号不保证准确，**一律给符号名**；非给行号不可时，在依据里注明「行号会漂」。
- 答案什么时候会过期？当 `依据` 指向的符号或文档 §N 变了的时候。所以依据写得越具体，失效越容易被发现。
- 定期（或大改代码后）可以拿库里每条的 `依据` 回去抽查一遍；抽不到的，把答案降级为 `未核` 或直接重写。

---

## 七、语气一致性

整库的答案都应当是**同一个人的口吻**：第一人称、短句、结论先行。

不要出现两种风格混杂——比如一半是「我认为」，一半是「系统采用了……」。后者是文档腔，念出来不像人话。

---

## 八、示例条目

```markdown
## Q7. 多路检索的结果怎么融合？为什么不用分数直接相加？

- **模块**：RAG 检索 · **类型**：设计
- **依据**：`docs/RAG检索实现.md` §三 · `retrieval/fusion.py::rrf_fuse`
- **证据强度**：读码

**一句话**：用的是加权 RRF，不是分数直接相加——两路分数量纲不同，直接加等于让分数尺度大的那一路主导。

**展开**：两路召回各出一个有序列表，按 `1/(k + 排名)` 加权累加，`k` 取 60，权重按检索路分别配。选 RRF 是因为它只看排名、不看分数，天然免疫量纲问题。代价是丢掉分数的绝对信息：0.9 对 0.3 的强命中，和 0.51 对 0.50 的两条，在 RRF 眼里差距一样大，所以某一路信噪比更高时靠调权重补，而不是回头用分数。已知的边界是：如果某一路召回质量本身崩了，权重压不住，这时候要修的是召回。

**可能被追问**
1. k 为什么取 60？→ 经验值，作用是压平排名靠前几名的差距；调大更平滑，调小更看重头部。
2. 两路结果重叠怎么办？→ 按文档 ID 归并，同一文档的各路排名分别计分后累加。
```

> 这个示例只示范格式与语气。实际参数以当次取证为准，**不可照抄**。
